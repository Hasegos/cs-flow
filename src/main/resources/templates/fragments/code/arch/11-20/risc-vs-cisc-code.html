같은 C 코드가 ISA마다 다른 명령어가 됨

// C: 포인터가 가리키는 값에 y를 더함
void add_to(int *p, int y) { *p += y; }

; x86-64 (Intel 문법): 메모리 피연산자를 직접 다루는 명령어 1개
add DWORD PTR [rdi], esi
ret

; RISC-V (RV64): load → 연산 → store
lw   a5, 0(a0)
addw a5, a5, a1
sw   a5, 0(a0)
ret

; AArch64 (Arm): RISC-V처럼 메모리 접근을 load/store 명령으로만 함
ldr w2, [x0]
add w2, w2, w1
str w2, [x0]
ret

x86-64에서는 add DWORD PTR [rdi], esi 한 명령어가 메모리에서 읽고, 더하고, 메모리에 다시 씁니다. RISC-V와 AArch64는 연산 명령어가 레지스터만 다루므로 load, 연산, store의 세 명령어로 나뉩니다. 이 출력은 컴파일러와 최적화 수준에 따라 달라질 수 있는 예시입니다. 배포판에 따라 x86-64 출력 앞에 endbr64가 붙기도 합니다. 직접 확인하려면 gcc -O2 -S로 어셈블리를 만들어 보거나 대상 아키텍처의 크로스 컴파일러를 쓰면 됩니다. 어느 쪽이 더 낫다는 뜻이 아니라, 같은 일을 표현하는 방식이 ISA 철학에 따라 달라진다는 것을 보여 줍니다.

명령어 길이 — 가변과 고정

; objdump -d 출력 예: 주소, 기계어 바이트, 어셈블리
; x86-64: 명령어마다 길이가 다름 (2바이트, 1바이트)
 0:  01 37             add DWORD PTR [rdi], esi
 2:  c3                ret

; RISC-V: 기본 명령어는 모두 4바이트 (압축 확장 C를 쓰지 않을 때)
 0:  00052783          lw   a5, 0(a0)
 4:  00b787bb          addw a5, a5, a1
 8:  00f52023          sw   a5, 0(a0)
 c:  00008067          ret

x86의 두 명령어는 2바이트와 1바이트로 길이가 다릅니다. 명령어의 길이는 앞의 바이트를 해석해야 알 수 있어서 시작 위치를 찾는 일이 앞에서 뒤로 이어집니다. RISC-V의 기본 명령어는 모두 4바이트라서 다음 명령어가 항상 4바이트 뒤에서 시작합니다. 위 기계어는 예시이며 컴파일러와 옵션에 따라 달라질 수 있습니다. 이 예시에서는 x86이 메모리 피연산자 덧셈을 명령어 하나(3바이트)로 처리해 코드가 작고, 고정 4바이트 RISC-V는 명령어 길이가 일정해 디코딩이 단순합니다. 다만 RISC-V에는 2바이트 압축(C) 확장이 있어 같은 코드가 더 작아질 수 있으므로, 실제 크기는 명령어 조합과 확장에 따라 달라집니다.

내 컴퓨터의 아키텍처 확인

# 리눅스/맥: 머신 아키텍처 (x86_64, aarch64 등)
uname -m

# 실행 파일이 어느 아키텍처용인지 확인
file ./server
# 예: ELF 64-bit LSB executable, x86-64 ...  또는  ... ARM aarch64 ...

# 컨테이너 이미지를 두 아키텍처용으로 빌드
docker buildx build --platform linux/amd64,linux/arm64 -t app:latest .

ISA가 다르면 기계어가 달라서 x86용 실행 파일은 Arm CPU에서 그대로 실행되지 않습니다. uname -m은 현재 머신의 아키텍처를, file 명령은 실행 파일이 어느 아키텍처용인지 알려 줍니다. Arm 기반 서버나 노트북을 함께 쓴다면 컨테이너 이미지를 linux/amd64와 linux/arm64 모두 빌드해 두는 방법이 있습니다. 여러 플랫폼 이미지를 로컬에 적재하려면 containerd 이미지 스토어를 켜야 하고, 그렇지 않으면 --push로 레지스트리에 올립니다. 인터프리터나 가상 머신 위에서 도는 코드(자바 바이트코드, 파이썬 스크립트)는 그 인터프리터가 해당 아키텍처를 지원하면 소스를 바꾸지 않고 실행됩니다.
