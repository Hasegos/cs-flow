거짓 공유 — 이웃한 원소를 서로 다른 스레드가 씀

// 두 스레드가 서로 다른 원소를 쓰지만 이웃해서 같은 캐시 라인에 놓일 수 있음
long[] counters = new long[2];
Thread t0 = new Thread(() -> { for (int i = 0; i < N; i++) counters[0]++; });
Thread t1 = new Thread(() -> { for (int i = 0; i < N; i++) counters[1]++; });

// 인덱스 간격을 띄움: long 8개 = 64바이트 떨어져 서로 다른 라인에 놓임(라인이 64바이트일 때)
long[] padded = new long[16];
// t0은 padded[0]을, t1은 padded[8]을 증가

첫 번째 배열에서 두 스레드는 서로 다른 변수를 쓰지만, 배열의 시작 주소는 JVM이 정하므로 항상 같은 라인이라고 보장되지는 않지만, 이웃한 8바이트 값은 대개 같은 64바이트 라인에 들어갑니다. 한쪽이 쓸 때마다 상대 코어의 라인이 무효화되어 라인이 코어 사이를 오갑니다. 두 번째 배열처럼 쓰는 위치를 64바이트 이상 띄우면 각 스레드가 자기 라인을 수정됨(M) 상태로 유지해 라인 이동이 사라집니다. 캐시 라인 크기는 CPU마다 다를 수 있으므로 64바이트는 흔한 값을 가정한 예입니다. 실제 속도 차이는 하드웨어와 JVM에 따라 다르므로 직접 측정해 확인해야 합니다.

경합을 줄이는 카운터 — AtomicLong과 LongAdder

// 모든 스레드가 같은 변수 하나를 갱신: 그 변수가 든 라인을 코어들이 서로 빼앗음
AtomicLong shared = new AtomicLong();
shared.incrementAndGet();

// 갱신이 경합하면 내부 변수를 여러 개로 나눠 가짐: 합계는 sum()으로 읽음
LongAdder adder = new LongAdder();
adder.increment();
long total = adder.sum();

여러 스레드가 동시에 같은 AtomicLong을 갱신하면 쓰기마다 그 변수가 든 캐시 라인의 독점 소유권이 코어 사이를 옮겨 다닙니다. 경합이 낮으면 이 비용은 작습니다. LongAdder는 경합이 생기면 합계를 여러 변수로 나눠 가져서 스레드들이 서로 다른 변수를 갱신하게 하고, 읽을 때 sum()으로 합칩니다. 대신 sum()을 호출하는 순간의 값은 갱신이 한창일 때 정확한 스냅샷이 아닐 수 있어, 통계처럼 자주 쓰고 가끔 읽는 값에 알맞습니다.

C++ — 카운터를 캐시 라인 단위로 정렬

// C++17: 거짓 공유를 피하기 위한 최소 간격(구현이 제공하는 상수)
#include <new>
#include <atomic>

struct alignas(std::hardware_destructive_interference_size) Counter {
    std::atomic<long> value{0};
};

Counter counters[2];  // 스레드 0은 counters[0], 스레드 1은 counters[1]만 사용

alignas로 구조체를 해당 간격에 정렬하면 배열의 각 원소가 서로 다른 캐시 라인에 놓이므로 이웃한 카운터를 서로 다른 스레드가 써도 거짓 공유가 생기지 않습니다. hardware_destructive_interference_size는 거짓 공유를 피하려고 서로 떼어 놓아야 할 최소 간격의 힌트입니다. 이름은 표준이 정하고 값은 구현이 정하며, 컴파일러 옵션과 타깃에 따라 달라질 수 있습니다. 구조체 크기가 라인 크기만큼 커지므로, 원소 수가 많은 배열에 이런 패딩을 쓰면 메모리를 많이 쓴다는 점도 함께 따져야 합니다.
