Java — 거스름돈 (그리디)

/* ── 큰 동전부터 확인하며, 쓸 수 있으면 계속 사용 ──────────── */
public List<Integer> makeChange(int amount, int[] coins) {
    // coins는 반드시 큰 단위 → 작은 단위 순으로 정렬되어 있어야 함
    List<Integer> used = new ArrayList<>();
    for (int coin : coins) {
        while (amount >= coin) {
            used.add(coin);
            amount -= coin;              // 결정을 절대 되돌리지 않음
        }
    }
    return used;                     // amount가 0이 되면 끝
}

반복문이 두 겹이지만, 안쪽 while은 동전 하나당 최대 몇 번만 반복되므로 전체 시간은 동전 종류 수에 비례합니다 — DP처럼 표를 채우지 않아 훨씬 빠릅니다.
이 코드가 항상 최소 개수를 보장하는 것은 coins 배열의 단위 관계(예: 500=100×5) 덕분입니다. 단위가 애매하면 이 가정이 깨집니다.

Java — 활동 선택 (그리디)

/* ── 종료 시간 기준 정렬 후, 겹치지 않으면 무조건 선택 ────── */
public List<Activity> selectActivities(List<Activity> activities) {
    activities.sort((a, b) -> a.end - b.end);   // 핵심: 종료 시간 오름차순 정렬

    List<Activity> selected = new ArrayList<>();
    int lastEnd = -1;
    for (Activity a : activities) {
        if (a.start >= lastEnd) {     // 마지막 선택과 안 겹치면
            selected.add(a);          // 무조건 선택 (되돌리지 않음)
            lastEnd = a.end;
        }
    }
    return selected;
}

a.start >= lastEnd 한 줄이 "겹치는지" 판단의 전부입니다 — 겹치지 않으면 무조건 선택하고, 그 선택을 절대 재검토하지 않습니다.
정렬에 O(n log n), 이후 한 번 훑는 데 O(n)이 걸려 전체 O(n log n)입니다. 모든 부분집합을 확인해야 하는 방식보다 압도적으로 빠릅니다.

Java — 그리디가 실패하는 예 (0/1 배낭 문제)

/* ── "가치 높은 순"으로 그리디하게 담으면? 최적해가 아닐 수 있음 ── */
public int greedyKnapsack(int[] weights, int[] values, int capacity) {
    // 가치 기준 내림차순 정렬 후, 담을 수 있으면 무조건 담기 (그리디)
    Integer[] idx = /* 가치 내림차순으로 정렬된 인덱스라고 가정 */ null;
    int totalValue = 0;
    for (int i : idx) {
        if (weights[i] <= capacity) {
            capacity -= weights[i];
            totalValue += values[i];     // 한 번 담으면 되돌리지 않음
        }
    }
    return totalValue;                  // algo-06의 DP 결과보다 작을 수 있음!
}

이 코드는 문법적으로는 멀쩡하지만, "가치가 높다고 먼저 담은 아이템"이 무게를 많이 차지해 뒤에 더 효율적인 조합을 막아버릴 수 있습니다.
algo-06(DP 기초)에서 같은 문제를 dp[i][w] 표로 풀었을 때와 결과를 비교해보면, 그리디가 항상 통하지 않는다는 것을 직접 확인할 수 있습니다 — "포함/제외를 전부 비교하지 않고 하나로 확정해버린" 대가입니다.
