SQL (PostgreSQL) — OFFSET과 커서 쿼리 비교

-- OFFSET 방식: 100,000번째 페이지 (페이지 크기 10)
SELECT * FROM post
ORDER BY id
LIMIT 10 OFFSET 999990;      -- 앞의 999,990행을 거쳐 건너뛴다

-- 커서 방식: 마지막으로 본 id가 999990
SELECT * FROM post
WHERE id > 999990
ORDER BY id
LIMIT 10;                      -- 인덱스로 그 위치부터 10행만 읽는다

두 쿼리는 같은 10행을 돌려주지만 DB가 하는 일이 다릅니다. OFFSET 쿼리는 정렬된 결과의 앞쪽 999,990행을 거쳐 건너뛴 뒤에야 10행을 돌려주고, 커서 쿼리는 id 인덱스에서 999990 다음 위치를 찾아 거기서부터 10행만 읽습니다. 둘 다 ORDER BY가 있어야 결과 순서가 정해집니다. 순서를 지정하지 않으면 LIMIT로 어떤 행이 나올지 예측할 수 없습니다. 커서 쿼리가 빠르려면 where와 order by에 쓰는 컬럼에 인덱스가 있어야 합니다. 기본 키인 id는 이미 인덱스가 있습니다. 실행 계획(EXPLAIN ANALYZE)으로 보면 OFFSET 쿼리는 offset이 커질수록 처리하는 행이 늘어나지만 커서 쿼리는 offset 값에 영향을 받지 않는다는 차이를 확인할 수 있습니다.

SQL (PostgreSQL) — 정렬 기준이 중복될 때의 복합 커서

-- 최신순 목록, 마지막으로 본 행은 (created_at = '2026-10-21 09:00', id = 4521)
SELECT * FROM post
WHERE (created_at, id) < ('2026-10-21 09:00', 4521)
ORDER BY created_at DESC, id DESC
LIMIT 10;

-- 이 조건을 받치는 복합 인덱스
CREATE INDEX idx_post_created_id ON post (created_at DESC, id DESC);

작성 시각은 같은 값을 가진 행이 여러 개일 수 있어서, 시각만으로 "마지막으로 본 위치"를 정하면 경계에서 같은 시각의 행이 건너뛰어질 수 있습니다. 그래서 고유한 id를 정렬 기준에 덧붙이고 (created_at, id) 쌍으로 비교합니다. where (created_at, id) < (값1, 값2)는 행 값 비교로, 먼저 created_at을 비교하고 같으면 id를 비교하는 사전순 규칙입니다. 정렬 방향(DESC)과 비교 방향(<)을 맞춰야 하고, ORDER BY도 같은 컬럼 순서로 써야 합니다. 정렬 기준과 같은 컬럼 순서의 복합 인덱스가 있으면 PostgreSQL은 행 값 비교를 인덱스 조건으로 쓸 수 있습니다. 모든 컬럼의 정렬 방향이 같으면 반대 방향으로 읽는 것도 가능합니다. 비교하는 컬럼에 NULL이 있으면 비교 결과가 NULL이 되어 행이 빠지므로 NOT NULL이어야 안전합니다. 시각과 id의 값은 이전 응답의 마지막 행에서 가져온 것이어야 합니다.

Java (Spring Data JPA) — OFFSET 방식 Page와 커서 방식 구현

public interface PostRepository extends JpaRepository<Post, Long> {

    // OFFSET 방식: Pageable을 받으면 limit/offset 쿼리 + (Page이면) count 쿼리가 실행된다
    Page<Post> findAllBy(Pageable pageable);

    // 커서 방식: 마지막으로 본 id보다 작은 것을 id 내림차순으로 size개
    List<Post> findByIdLessThanOrderByIdDesc(Long lastId, Pageable pageable);
}

// 서비스: 첫 요청은 cursor가 null
List<Post> next(Long cursor, int size) {
    long last = (cursor == null) ? Long.MAX_VALUE : cursor;
    return postRepository.findByIdLessThanOrderByIdDesc(last, PageRequest.of(0, size));
}

Pageable을 받는 Page 반환 메서드는 limit와 offset을 붙인 쿼리에 더해 보통 전체 개수를 위한 count 쿼리도 실행합니다. 전체 페이지 수를 보여 주려면 필요하지만 큰 테이블에서는 count 자체가 부담입니다. 개수가 필요 없다면 Slice를 반환하게 해 count를 피할 수 있습니다. 커서 방식은 "마지막으로 본 id보다 작은 것"이라는 조건 메서드로 만들었습니다. PageRequest.of(0, size)는 항상 첫 페이지(offset 0)에 size개를 달라는 뜻이어서 위치는 where 조건이 정합니다. 응답에는 마지막 행의 id를 다음 커서로 함께 내려 주면 됩니다. Spring Data의 키셋 스크롤(ScrollPosition, Window) 기능을 쓰면 이런 쿼리와 커서 관리를 프레임워크가 처리해 주기도 합니다. 위 코드는 원리를 보이려는 단순한 예시이며 id는 고유하고 내림차순 정렬이 가능한 값이어야 합니다.

HTTP — 커서 응답과 다음 요청의 모양

# 첫 요청
GET /posts?size=10

# 응답: 데이터와 다음 커서
{
  "items": [ { "id": 100, ... }, ... , { "id": 91, ... } ],
  "nextCursor": "eyJpZCI6OTF9",   // {"id":91}을 Base64로 인코딩한 불투명 값
  "hasNext": true
}

# 다음 요청: 받은 커서를 그대로 돌려준다
GET /posts?size=10&cursor=eyJpZCI6OTF9

커서 방식 API는 응답에 다음 요청에 쓸 커서를 함께 내려 줍니다. 클라이언트는 이 값의 내용을 해석하지 않고 그대로 다음 요청에 돌려주기만 합니다. 서버가 내부 키를 인코딩해 주면 나중에 정렬 기준을 바꿔도 클라이언트를 고치지 않아도 됩니다. hasNext는 다음 데이터가 더 있는지 알려 줍니다. 구현할 때는 size보다 하나 더 읽어 보고 남는 행이 있는지 확인하는 방법을 흔히 씁니다. 위 인코딩 값은 설명을 위한 예시입니다. 커서는 클라이언트가 바꿀 수 있는 입력이므로 서버가 값을 검증해야 합니다. OFFSET 방식 API는 page 번호나 offset을 그대로 노출하지만, 커서 방식은 "어디까지 봤는지"를 서버가 만든 표식으로 주고받는다는 점이 다릅니다.
