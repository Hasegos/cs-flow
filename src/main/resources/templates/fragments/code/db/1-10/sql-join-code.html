SQL — INNER / LEFT / RIGHT JOIN

-- INNER JOIN: 양쪽 모두 값이 있는 행만
SELECT u.id, u.name, o.id AS order_id, o.product
FROM users u
INNER JOIN orders o ON o.user_id = u.id;

-- LEFT JOIN: USERS 전부 + 짝 없는 ORDERS는 NULL
SELECT u.id, u.name, o.id AS order_id, o.product
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- RIGHT JOIN: ORDERS 전부 + 짝 없는 USERS는 NULL
SELECT u.id, u.name, o.id AS order_id, o.product
FROM users u
RIGHT JOIN orders o ON o.user_id = u.id;

세 쿼리의 FROM/ON 절은 완전히 동일하고, JOIN 키워드만 다릅니다 — 시각화의 벤 다이어그램에서 강조 영역이 바뀌는 것과 같은 지점입니다.
LEFT JOIN 결과에서 박도윤처럼 주문이 없는 사용자는 order_id, product가 NULL로 나옵니다.

Java — JPQL에서 LEFT JOIN FETCH로 N+1 방지

public interface UserRepository extends JpaRepository<User, Long> {

    // LEFT JOIN FETCH: 주문이 없는 사용자도 결과에 포함(= LEFT JOIN),
    // 연관된 Order를 한 번에 가져와 LazyInitializationException도 방지
    @Query("SELECT DISTINCT u FROM User u LEFT JOIN FETCH u.orders")
    List<User> findAllWithOrders();
}

이 프로젝트 규칙상 연관 엔티티를 조회할 땐 항상 LEFT JOIN FETCH를 씁니다 — INNER JOIN FETCH를 쓰면 주문이 없는 User(박도윤)가 결과에서 통째로 빠져버리기 때문입니다.
즉 "연관 데이터를 함께 가져오고 싶다"는 이유만으로도, 의도치 않게 INNER JOIN의 필터링 효과가 발생할 수 있다는 점을 이 시각화의 INNER 탭과 비교해서 기억해두면 좋습니다.

SQL — MySQL에서 FULL OUTER JOIN 흉내내기

-- MySQL은 FULL OUTER JOIN 문법이 없어서 UNION으로 대체
SELECT u.id, u.name, o.id AS order_id, o.product
FROM users u
LEFT JOIN orders o ON o.user_id = u.id

UNION

SELECT u.id, u.name, o.id AS order_id, o.product
FROM users u
RIGHT JOIN orders o ON o.user_id = u.id;

LEFT JOIN 결과(USERS 전부)와 RIGHT JOIN 결과(ORDERS 전부)를 UNION으로 합치면, 겹치는 행은 자동으로 한 번만 남고 양쪽의 unmatched 행은 모두 살아남습니다.
이 시각화의 FULL 탭에서 4행(박도윤의 NULL 행 + user_id=5 주문의 NULL 행 포함)이 나오는 것과 정확히 같은 결과입니다.
