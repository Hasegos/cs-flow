SQL — PostgreSQL 선언적 파티셔닝

CREATE TABLE orders (
    id bigint, ordered_at date NOT NULL, region text, amount int
) PARTITION BY RANGE (ordered_at);                 -- 파티션 키 = ordered_at

CREATE TABLE orders_2024_01 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');   -- 상한은 포함하지 않음
CREATE TABLE orders_2024_02 PARTITION OF orders
    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');

EXPLAIN SELECT * FROM orders
WHERE ordered_at = '2024-02-15';                      -- 계획에 orders_2024_02만 나온다 (프루닝)

ALTER TABLE orders DETACH PARTITION orders_2024_01;       -- 오래된 파티션을 떼어 내고
DROP TABLE orders_2024_01;                              -- 통째로 삭제 (대량 DELETE와 다름)

-- List와 Hash도 같은 형태
-- PARTITION BY LIST (region)   ... FOR VALUES IN ('KR')
-- PARTITION BY HASH (id)       ... FOR VALUES WITH (MODULUS 4, REMAINDER 0)

PostgreSQL의 선언적 파티셔닝은 PARTITION BY로 방식(RANGE, LIST, HASH)과 키를 정하고, 파티션마다 PARTITION OF와 FOR VALUES로 담당 범위를 지정합니다. 파티션을 나눈 부모 테이블 orders 자체에는 행이 저장되지 않고, 행은 키 값에 맞는 파티션에 들어갑니다. Range의 FROM은 포함하고 TO는 포함하지 않으므로 1월 파티션과 2월 파티션의 범위가 겹치지 않습니다. WHERE에 파티션 키 조건이 있으면 EXPLAIN 결과에 해당 파티션만 나오고, 시각화의 파티션 프루닝 탭이 보여 주는 동작과 같습니다. 오래된 기간의 데이터는 DETACH PARTITION으로 떼어 내 DROP TABLE로 지우면 대량 DELETE처럼 행마다 삭제하고 정리하는 부담이 없습니다. 다만 DROP이나 DETACH PARTITION은 부모 테이블에 강한 잠금이 필요하고(DETACH PARTITION ... CONCURRENTLY는 더 약한 잠금), 어느 파티션에도 맞지 않는 값의 INSERT는 오류이므로 필요하면 DEFAULT 파티션을 둡니다. 시각화의 month는 날짜의 월에 해당합니다.

Python — 행 배정과 프루닝 흉내

from collections import defaultdict

rg = ('KR', 'KR', 'US', 'JP', 'KR', 'US')
rows = [{'id': i + 1, 'month': 1 if i < 6 else 2 if i < 11 else 3 if i < 18 else 4,
         'region': rg[i % 6]} for i in range(24)]

def route(row, scheme):
    if scheme == 'range': return f"p_2024_{row['month']:02d}"   # 값 범위
    if scheme == 'list':  return f"p_{row['region']}"           # 값 목록
    return f"p_{row['id'] % 4}"                                 # 해시 (id % 4로 단순화)

def partitions(scheme):
    parts = defaultdict(list)
    for r in rows:
        parts[route(r, scheme)].append(r)
    return parts

def scan(scheme, key, value):           # 키 조건이면 프루닝, 아니면 전부 읽음
    parts = partitions(scheme)
    names = [f'p_2024_{value:02d}'] if (scheme, key) == ('range', 'month') else list(parts)
    return names, sum(len(parts[n]) for n in names)

for s in ('range', 'list', 'hash'):
    print(s, {k: len(v) for k, v in sorted(partitions(s).items())})
print(scan('range', 'month', 3))
print(scan('range', 'region', 'KR'))
# range {'p_2024_01': 6, 'p_2024_02': 5, 'p_2024_03': 7, 'p_2024_04': 6}
# list {'p_JP': 4, 'p_KR': 12, 'p_US': 8}
# hash {'p_0': 6, 'p_1': 6, 'p_2': 6, 'p_3': 6}
# (['p_2024_03'], 7)
# (['p_2024_01', 'p_2024_02', 'p_2024_03', 'p_2024_04'], 24)

같은 24행을 세 방식으로 배정하는 장난감 모델입니다. route가 행마다 담당 파티션 이름을 정하고, 출력은 Range가 6, 5, 7, 6행, List가 JP 4행, KR 12행, US 8행, Hash가 6행씩입니다. 시각화의 분할 방식 탭과 같은 결과이고, 해시는 설명을 위해 id % 4로 단순화했습니다. 실제 데이터베이스의 해시 함수와 다릅니다. scan은 프루닝을 흉내 냅니다. 파티션 키인 month 조건으로 찾으면 3월 파티션 하나에서 7행만 보지만, 키가 아닌 region으로 찾으면 파티션 4개 24행을 모두 훑습니다. 시각화의 파티션 프루닝 탭과 같은 결과입니다.

Java — TreeMap으로 Range 경계 찾기

TreeMap<Integer, String> bounds = new TreeMap<>();       // 키 = 파티션이 시작되는 month
bounds.put(1, "p_2024_01");
bounds.put(2, "p_2024_02");
bounds.put(3, "p_2024_03");
bounds.put(4, "p_2024_04");

int[] months = new int[24];
for (int i = 0; i < 24; i++) months[i] = i < 6 ? 1 : i < 11 ? 2 : i < 18 ? 3 : 4;

Map<String, Integer> count = new TreeMap<>();
for (int m : months) count.merge(bounds.floorEntry(m).getValue(), 1, Integer::sum);
System.out.println(count);                          // {p_2024_01=6, p_2024_02=5, p_2024_03=7, p_2024_04=6}

int[] hash = new int[4];
for (int id = 1; id <= 24; id++) hash[id % 4]++;
System.out.println(Arrays.toString(hash));            // [6, 6, 6, 6]

자바에서는 TreeMap의 floorEntry가 값 이하에서 가장 큰 경계를 찾아 주므로 Range 파티션의 경계 검색을 간단히 표현할 수 있습니다. month 1부터 4까지를 경계로 두고 24행을 배정하면 6, 5, 7, 6행이 나옵니다. 경계가 많아져도 TreeMap은 트리 구조라 O(log n)에 찾으므로 비용이 크게 늘지 않습니다. 아래쪽은 Hash 배정을 id % 4로 단순화한 것으로 4개 파티션에 6행씩 들어갑니다. 실제 파티셔닝은 데이터베이스가 직접 처리하며 응용 프로그램이 이렇게 경계를 찾는 일은 거의 없습니다. 이 코드는 개념 설명용입니다. 상한을 검사하지 않아 month 5 이상도 마지막 파티션으로 배정되고 1보다 작으면 null이라 오류가 나는데, 실제 PostgreSQL은 이런 값을 오류 또는 DEFAULT 파티션으로 처리합니다.
