SQL — 정규화 전(비정규형) vs 정규화 후(3NF)

-- 정규화 전: 한 테이블에 모든 게 뒤섞여 있고, products는 콤마로 여러 값
CREATE TABLE orders_raw (
    order_id    BIGINT PRIMARY KEY,
    user_name   VARCHAR(50),
    user_grade  VARCHAR(10),
    products    VARCHAR(200)   -- '노트북, 마우스' — 1NF 위반
);

-- 정규화 후(3NF): 세 테이블로 분리, 각 non-key 컬럼은 자기 테이블의 PK에만 의존
CREATE TABLE users (
    user_name   VARCHAR(50) PRIMARY KEY,
    user_grade  VARCHAR(10)  NOT NULL
);

CREATE TABLE orders (
    order_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_name   VARCHAR(50) NOT NULL,
    FOREIGN KEY (user_name) REFERENCES users(user_name)
);

CREATE TABLE order_items (
    order_id    BIGINT      NOT NULL,
    product     VARCHAR(50) NOT NULL,
    PRIMARY KEY (order_id, product),
    FOREIGN KEY (order_id) REFERENCES orders(order_id)
);

이 시각화의 3NF 탭 결과와 정확히 같은 구조입니다 — users.user_grade는 더 이상 주문 정보에 끌려다니지 않고, 사용자 한 명당 딱 한 번만 저장됩니다.
김민준의 등급이 바뀌면 users 테이블 딱 한 행만 UPDATE하면 됩니다 — 정규화 전이었다면 김민준의 주문이 100건이면 100행을 다 고쳐야 했을 것입니다.

Java — 정규화된 구조를 그대로 반영한 JPA 엔티티

@Entity
public class User {
    @Id
    private String userName;
    private String userGrade;
}

@Entity
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_name")
    private User user;              // user_grade는 여기 없다 — User를 통해서만 접근

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
    private List<OrderItem> items = new ArrayList<>();
}

@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private Order order;
    private String product;
}

Order에는 userGrade 필드가 없습니다 — 등급이 필요하면 반드시 order.getUser().getUserGrade()처럼 User를 거쳐야 합니다.
이렇게 필드를 직접 두지 않는 것 자체가 "이행 종속을 만들지 않는다"는 3NF 규칙을 코드로 강제하는 방법입니다.

Java — (참고) 조회 성능을 위한 반정규화

@Entity
public class Order {
    // ...

    // 원칙적으로는 3NF 위반(이행 종속)이지만,
    // "주문 목록에 등급 뱃지 표시"가 매번 JOIN을 유발해 느리다면
    // 의도적으로 복제해 두는 경우가 있다 (반정규화)
    private String userGradeSnapshot;
}

이 시각화의 "정규화의 대가" 카드에서 언급한 트레이드오프가 바로 이것입니다 — userGradeSnapshot은 등급이 바뀌면 여러 곳을 고쳐야 하는 대신, 조회할 때 User와의 JOIN을 피할 수 있습니다.
이런 선택은 "정규화 규칙을 모르고 어긴 것"과 "알고서 성능을 위해 의도적으로 어긴 것"의 차이이므로, 반정규화는 항상 팀 안에서 합의하고 문서로 남겨야 합니다.
