Java — @Transactional로 이체 서비스 구현

@Service
@RequiredArgsConstructor
public class TransferService {

    private final AccountRepository accountRepository;

    @Transactional
    public void transfer(Long fromId, Long toId, long amount) {
        Account from = accountRepository.findById(fromId)
                .orElseThrow(() -> new NotFoundException("계좌 없음: " + fromId));
        Account to = accountRepository.findById(toId)
                .orElseThrow(() -> new NotFoundException("계좌 없음: " + toId));

        from.withdraw(amount);   // 첫 번째 UPDATE에 해당

        if (to.isFrozen()) {
            throw new IllegalStateException("계좌가 정지 상태라 입금할 수 없습니다.");
        }
        to.deposit(amount);      // 두 번째 UPDATE에 해당
    }
}

withdraw() 이후 예외가 던져지면, @Transactional이 감싸고 있는 이 메서드 전체가 RuntimeException 기준으로 자동 ROLLBACK됩니다 — 이미 반영된 from.withdraw()도 함께 취소됩니다.
이 시각화의 "롤백(실패)" 탭에서 두 번째 UPDATE가 "계좌가 정지 상태"로 실패하는 것과 정확히 같은 상황입니다.

SQL — @Transactional이 내부적으로 실행하는 것

START TRANSACTION;

UPDATE accounts SET balance = balance - 20000 WHERE id = 1;
UPDATE accounts SET balance = balance + 20000 WHERE id = 2;

-- 둘 다 성공하면:
COMMIT;

-- 하나라도 실패하면(애플리케이션 예외 포함):
ROLLBACK;

@Transactional이 붙은 메서드에 진입하는 순간 START TRANSACTION이, 정상 종료되면 COMMIT이, 예외가 던져지면 ROLLBACK이 자동으로 실행됩니다.
즉 개발자가 직접 COMMIT/ROLLBACK을 호출하지 않아도, 메서드의 정상/예외 종료 여부만으로 트랜잭션 경계가 결정됩니다.

Java — 흔한 함정: 같은 클래스 안에서 호출하면 롤백이 안 걸림

@Service
public class OrderService {

    public void placeOrder(Long userId) {
        // this.saveOrder(userId) — 프록시를 거치지 않는 내부 호출!
        saveOrder(userId);          // @Transactional이 적용되지 않는다
    }

    @Transactional
    public void saveOrder(Long userId) {
        // ...
    }
}

@Transactional은 스프링이 만든 프록시 객체를 거쳐야 동작하는데, 같은 클래스 안에서 this.saveOrder()처럼 직접 호출하면 프록시를 우회해서 트랜잭션이 아예 시작되지 않습니다.
해결책은 saveOrder()를 별도의 @Service로 분리해서 주입받아 호출하는 것입니다 — 이 프로젝트의 생성자 주입(@RequiredArgsConstructor) 규칙과도 자연스럽게 맞물립니다.
