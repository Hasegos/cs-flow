nginx, curl — HTTP/3 켜고 확인하기

# nginx.conf (HTTP/3를 지원하게 빌드된 nginx 1.25 이상)
server {
    listen 443 quic reuseport;     # UDP 443: HTTP/3
    listen 443 ssl;                # TCP 443: HTTP/2, HTTP/1.1 (대비용)
    http2 on;                      # nginx 1.25.1 이상
    http3 on;

    ssl_certificate     /etc/ssl/example.crt;
    ssl_certificate_key /etc/ssl/example.key;

    add_header Alt-Svc 'h3=":443"; ma=86400';
}

# 확인: Alt-Svc 헤더와 HTTP/3 응답
curl -sI https://www.example.com/ | grep -i alt-svc
curl --http3-only -I https://www.example.com/

HTTP/3는 QUIC 위에서 UDP로 동작하므로 nginx는 listen 443 quic으로 UDP 443 포트를 따로 열고, http3 on으로 HTTP/3를 켭니다. 같은 포트의 TCP에서는 listen 443 ssl과 http2 on(nginx 1.25.1 이상)으로 HTTP/2와 HTTP/1.1을 계속 처리합니다. 브라우저는 처음에 TCP로 접속해 응답의 Alt-Svc 헤더에서 이 서버가 h3를 지원한다는 것을 알고, 이후 요청부터 HTTP/3를 시도합니다. ma는 이 정보를 기억하는 시간(초)이며, UDP가 막힌 네트워크에서는 TCP로 대신 접속합니다. curl의 --http3-only 옵션은 HTTP/3를 지원하게 빌드된 curl에서만 동작하며, HTTP/3가 안 되면 다른 버전으로 대체하지 않고 실패합니다(--http3는 대체합니다). 방화벽에서 UDP 443이 열려 있어야 HTTP/3가 쓰입니다.

Python — 첫 응답까지 걸리는 시간 계산

RTT = 50                       # 왕복 시간 (ms)

def first_response(handshake_rtts):
    # 핸드셰이크 왕복 수 + 요청 · 응답 1왕복
    return (handshake_rtts + 1) * RTT

print(first_response(2))      # TCP 1 + TLS 1.3 1  -> 150
print(first_response(1))      # QUIC (TLS 1.3 통합)  -> 100
print(first_response(0))      # QUIC 0-RTT 재연결   -> 50

첫 응답이 도착하는 시간은 핸드셰이크에 쓰는 왕복 수에 요청과 응답의 1왕복을 더한 값에 RTT를 곱한 것입니다. 서버 처리 시간은 뺀 단순한 계산입니다. TCP는 연결 수립에 1 RTT, TLS 1.3 핸드셰이크에 1 RTT가 필요해 2를 넣고, QUIC은 전송과 TLS 1.3 핸드셰이크를 합쳐 1 RTT이므로 1을 넣습니다. 전에 접속한 서버와의 0-RTT 재연결은 첫 패킷에 요청을 실어 보내므로 0입니다. 이 값은 시각화의 연결 수립 탭이 보여 주는 150ms, 100ms, 50ms와 같으며, RTT가 클수록 차이도 그만큼 커집니다.

Python — 패킷 유실 때의 전달 가능 패킷 비교

WIRE = [(s, n) for n in range(1, 4) for s in "ABC"]   # A1 B1 C1 A2 ...
received = set(WIRE) - {("A", 2)}                  # A2가 유실됨

def deliver_tcp(received):
    out = []
    for pkt in WIRE:                 # 연결 전체의 순서를 지킴
        if pkt not in received:
            break
        out.append(pkt)
    return out

def deliver_quic(received):
    out = []
    for s in "ABC":                  # 스트림마다 순서를 지킴
        n = 1
        while (s, n) in received:
            out.append((s, n))
            n += 1
    return out

print(len(deliver_tcp(received)), len(deliver_quic(received)))   # 3 7

WIRE는 스트림 A, B, C의 패킷이 번갈아 도착하는 순서이고, 그 가운데 A2가 유실된 상황을 만듭니다. deliver_tcp는 연결 전체의 순서를 지키므로 첫 빈자리(A2)를 만나면 멈추고, 그 앞의 A1, B1, C1 세 개만 애플리케이션에 전달합니다. deliver_quic은 스트림마다 순서를 따로 지키므로 스트림 A는 A1에서 멈추지만 스트림 B와 C는 끝까지 전달해 모두 7개를 전달합니다. 이 차이가 TCP 위의 HTTP/2에서 생기는 HOL 블로킹과 HTTP/3에서 줄어드는 이유이며, 시각화의 패킷 유실 탭과 같은 결과입니다. 실제 QUIC은 유실된 패킷을 재전송해 결국 모든 데이터를 전달합니다.
