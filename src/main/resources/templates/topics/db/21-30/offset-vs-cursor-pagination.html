오프셋 vs 커서 페이지네이션

태그

목록을 여러 페이지로 나누어 가져올 때, 다음 데이터를 어떻게 이어서 가져오는가가 페이지네이션 방식입니다. 방식에 따라 뒤쪽 페이지로 갈수록 느려지거나, 목록을 넘기는 동안 데이터가 바뀌면 방금 본 글이 다음 페이지에 또 나오는 문제가 생깁니다. 흔히 쓰는 OFFSET 방식은 위치를 번호로 기억하고, 커서(keyset) 방식은 마지막으로 본 행의 키를 기억합니다.

이 토픽에서는 100만 행 테이블을 10개씩 나누어 보며, OFFSET이 뒤쪽 페이지로 갈수록 거치는 행이 늘어나는 모습, 커서 방식이 위치와 상관없이 일정한 비용으로 이어지는 모습, 그리고 페이지를 넘기는 사이 데이터가 바뀔 때 두 방식의 결과가 어떻게 달라지는지를 단계별로 비교합니다.

핵심 개념

OFFSET / LIMIT

LIMIT는 가져올 행 수, OFFSET은 앞에서 건너뛸 행 수입니다. 페이지 번호를 (page − 1) × size로 바꿔 쓰면 원하는 페이지로 바로 이동할 수 있습니다.

핵심 개념

커서(keyset) 방식

마지막으로 받은 행의 정렬 키를 다음 요청에 실어 "그 키 뒤의 행"을 요청하는 방식입니다. where 조건과 인덱스로 위치를 바로 찾아 키셋(keyset) 또는 seek 방식이라고도 부릅니다.

핵심 개념

건너뛴 행의 비용

OFFSET으로 건너뛰는 행도 DB가 정렬 순서대로 거쳐야 합니다. 그래서 돌려주는 행은 10개여도 offset이 클수록 실제로 처리하는 행이 늘어납니다.

핵심 개념

고유한 정렬 기준

LIMIT를 쓸 때는 결과 순서가 항상 같게 정해지는 ORDER BY가 필요합니다. 작성 시각처럼 중복될 수 있는 값으로 정렬한다면 고유한 id를 함께 정렬 기준에 넣어야 합니다.

핵심 개념

복합 커서와 행 값 비교

정렬 기준이 (작성 시각, id)처럼 둘 이상이면 커서도 둘을 함께 담습니다. PostgreSQL은 where (created_at, id) < (값1, 값2)처럼 행 값을 사전순으로 비교하는 문법을 지원합니다.

핵심 개념

불투명 커서

API가 커서를 내부 키 그대로 주지 않고 인코딩한 문자열로 주면, 클라이언트가 내용을 해석해 의존하지 않게 되어 나중에 정렬 기준을 바꾸기 쉽습니다.

OFFSET은 구현이 쉽고 페이지 번호 UI에 맞습니다 — 임의의 페이지로 바로 이동할 수 있고 전체 페이지 수도 계산할 수 있어, 데이터가 작거나 깊은 페이지까지 가지 않는 화면에서는 충분합니다.
OFFSET의 약점은 깊은 페이지와 변하는 데이터입니다 — 뒤쪽 페이지일수록 느려지고, 앞쪽 데이터가 추가 · 삭제되면 중복이나 누락이 생깁니다.
커서 방식은 뒤쪽 위치에서도 거치는 행이 늘지 않습니다 — 정렬 기준에 맞는 인덱스가 있으면 기준 행 다음부터 바로 읽기 때문에 건너뛰는 행이 없고, 데이터가 바뀌어도 기준 행 다음으로 이어집니다.
커서 방식은 순차 이동에만 맞습니다 — "50페이지로 바로 이동"은 할 수 없어, 무한 스크롤이나 다음 · 이전 버튼에 어울립니다.
이 시각화에서 확인할 것 — "OFFSET 페이지네이션" 탭에서 거치는 행이 20개에서 약 100만 개로 늘어나는 과정을, "커서 페이지네이션" 탭에서 항상 10행만 읽는 모습을, "데이터가 바뀔 때" 탭에서 중복과 누락이 생기는 차이를 STEP으로 확인하세요.

배경

PostgreSQL과 MySQL은 LIMIT와 OFFSET 문법으로, SQL:2008 표준은 OFFSET ... FETCH FIRST ... ROWS ONLY로 결과의 일부만 돌려받는 기능을 제공합니다. 페이지 번호를 offset으로 바꾸기 쉬워 목록 페이지네이션에 쓰입니다. GraphQL 공식 문서는 오프셋 방식이 큰 데이터에서 성능과 보안 면의 단점이 있고, 새 레코드가 추가되면 이후 페이지의 오프셋 계산이 모호해질 수 있다고 설명합니다. 그래서 마지막으로 본 행을 기준으로 이어 가는 커서 방식을 권하며, GraphQL의 Relay 커넥션 규약도 커서를 기본 모델로 삼습니다.

숫자로 확인하기

OFFSET 값 — 페이지 크기 10에서 100,000번째 페이지는 offset이 999,990입니다. DB는 앞의 999,990행을 거쳐 건너뛴 뒤 10행을 돌려주므로 처리하는 행이 약 100만 개입니다.
처리하는 행 수 — OFFSET 방식은 offset + size, 커서 방식은 인덱스로 위치를 찾으므로 size개입니다. 1페이지는 둘 다 10개이지만 10만 페이지는 약 100만 대 10입니다.
변경 시 어긋남 — 최신순 목록에서 1페이지를 본 뒤 새 글이 3개 올라오면 OFFSET 2페이지에 이미 본 글 3개가 다시 나옵니다. 반대로 1페이지의 글이 하나 삭제되면 2페이지가 한 칸 앞으로 당겨져 다음 글 하나가 건너뛰어집니다.
검색 엔진의 한계 — Elasticsearch는 from + size를 기본 10,000개까지만 허용하고(index.max_result_window), 그보다 깊은 곳은 마지막 정렬 값으로 이어 가는 search_after를 쓰도록 안내합니다.

자주 하는 오해

인덱스를 걸면 OFFSET도 빨라진다 — 인덱스는 정렬을 생략하게 해 줄 뿐, offset만큼의 행을 거치는 비용은 남아서 큰 offset에서는 인덱스를 써도 느려질 수 있습니다.
커서 방식은 항상 OFFSET보다 낫다 — 페이지 번호로 이동하거나 전체 페이지 수를 보여 주는 화면에는 맞지 않습니다. 용도가 순차 탐색인지 임의 이동인지가 선택 기준입니다.
ORDER BY 없이 LIMIT만 써도 된다 — 순서가 정해지지 않은 결과에 LIMIT를 걸면 어떤 행이 나올지 예측할 수 없고, 호출마다 다른 행이 나와 중복과 누락이 생깁니다.
작성 시각만 커서로 쓰면 된다 — 같은 시각에 여러 행이 있으면 경계에서 행이 건너뛰어질 수 있습니다. 고유한 id를 함께 넣어 (작성 시각, id)로 비교해야 합니다.

면접에서 이렇게 물어요

면접 질문

OFFSET 페이지네이션의 문제점은 무엇인가요?

OFFSET만큼의 행을 DB가 거쳐 건너뛰어야 해서 뒤쪽 페이지일수록 느려지고, 페이지를 넘기는 사이 앞쪽 데이터가 추가나 삭제되면 같은 글이 중복되거나 어떤 글이 누락됩니다.

면접 질문

커서 방식은 어떻게 동작하고 단점은 무엇인가요?

마지막으로 받은 행의 정렬 키를 where 조건으로 넘겨 그 뒤 행만 인덱스로 읽습니다. 정렬 기준에 맞는 인덱스가 있으면 위치와 무관하게 읽는 행 수가 같고 변경에 강하지만, 임의 페이지로 바로 이동할 수 없고 전체 개수는 별도 COUNT로 구해야 합니다.

면접 질문

정렬 기준이 중복되면 커서를 어떻게 만드나요?

고유한 키를 정렬 기준에 덧붙여 (작성 시각, id) 같은 복합 기준으로 정렬하고, 커서도 그 두 값을 담아 where (created_at, id) < (값1, 값2)처럼 사전순으로 비교합니다. 복합 인덱스가 있으면 효율적으로 읽습니다.

면접 질문

무한 스크롤 피드에는 어떤 방식이 맞나요?

새 글이 계속 올라오고 사용자가 순서대로만 내려가므로 커서 방식이 잘 맞습니다. 변경에도 중복이 없고 깊은 곳까지 일정한 비용으로 읽을 수 있습니다.

실제 시스템에서는

Spring Data — Pageable과 Page는 OFFSET 방식이고 Page는 보통 전체 개수를 위한 count 쿼리를 추가로 실행합니다(결과가 덜 찬 경우 등에는 생략될 수 있음). 개수가 필요 없으면 Slice를 쓰고, 최근 버전의 Spring Data는 키셋 기반 스크롤(ScrollPosition, Window)도 제공합니다.
공개 API — Stripe는 목록 API에서 starting_after, ending_before 커서를 쓰고, GitHub GraphQL API는 first, after 인자와 커서로 이어 가는 커넥션을 씁니다.
검색과 NoSQL — Elasticsearch는 깊은 페이지에 search_after를, DynamoDB는 LastEvaluatedKey와 ExclusiveStartKey로 이어 읽는 커서형 방식을 씁니다.
전체 개수 표시 — 페이지 번호 UI는 총 개수를 세는 COUNT가 필요한데, PostgreSQL처럼 MVCC에서 행의 가시성을 확인해야 하는 DB에서는 큰 테이블의 COUNT가 전체 행이나 인덱스를 훑는 일이 되어 비쌀 수 있습니다. 그래서 "다음" 버튼만 두거나 근사값을 쓰기도 합니다.

함께 보면 좋은 토픽

인덱스 — 커서 조건이 인덱스로 위치를 찾는 원리를 봅니다.
실행 계획 — OFFSET 쿼리가 몇 행을 거치는지 실행 계획으로 확인합니다.
N+1 문제 — 목록 API에서 쿼리 횟수가 늘어나는 또 하나의 대표 문제를 봅니다.
트랜잭션 격리 수준 — 읽는 도중 데이터가 바뀔 때 보이는 값이 어떻게 달라지는지 봅니다.
