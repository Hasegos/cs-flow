N+1 문제

태그

목록을 가져오는 쿼리 1번 뒤에, 목록의 각 항목에 딸린 데이터를 가져오는 쿼리가 항목 수 N번 따로 실행되는 현상이 N+1 문제입니다. 데이터가 적을 때는 티가 나지 않다가 데이터가 늘면 거의 같은 모양의 SELECT 문이 수십, 수백 번 반복되며 느려집니다. JPA 같은 ORM을 쓰면 코드에는 반복문 하나만 보이기 때문에 쿼리가 몇 번 나가는지 눈치채기 어렵습니다.

이 토픽에서는 팀 목록과 팀별 멤버 목록을 예로, N+1이 왜 생기는지, 조인 페치로 쿼리를 1번으로 줄이는 방법과 그 한계(페이징), 지연 로딩을 유지한 채 IN으로 묶어 가져오는 배치 페치를 쿼리 횟수를 세며 비교합니다.

핵심 개념

N+1 문제

목록 조회 쿼리 1번과 목록의 각 항목마다 연관 데이터를 가져오는 쿼리 N번이 따로 실행되는 현상입니다. 항목이 늘면 쿼리 수도 비례해서 늘어납니다.

핵심 개념

지연 로딩(LAZY)

연관된 엔티티나 컬렉션을 처음 사용하는 순간에 쿼리를 실행하는 방식입니다. 필요 없는 데이터를 미리 읽지 않는 장점이 있지만, 반복문 안에서 쓰면 N+1의 원인이 됩니다.

핵심 개념

즉시 로딩(EAGER)

엔티티를 읽을 때 연관 엔티티도 함께 로딩하는 방식입니다. 즉시 로딩으로 바꾼다고 N+1이 사라지지는 않습니다. JPQL 쿼리에는 즉시 로딩 설정이 조인으로 적용되지 않아, 먼저 쿼리를 실행한 뒤 연관 데이터를 추가 쿼리로 가져오기 때문입니다.

핵심 개념

조인 페치(join fetch)

JPQL에서 연관 데이터를 같은 쿼리에서 조인해 가져오라고 지시하는 방식입니다. 쿼리가 1번으로 줄지만 컬렉션을 조인하면 결과 행이 부모보다 많아집니다. 같은 부모가 자식 수만큼 반복되기 때문입니다.

핵심 개념

엔티티 그래프(@EntityGraph)

Spring Data JPA의 쿼리 메서드에 붙여 어떤 연관을 함께 로딩할지 선언하는 방법입니다. 내부 동작은 join fetch와 비슷하게 연관 데이터를 한 번에 가져옵니다.

핵심 개념

배치 페치(batch fetch)

지연 로딩은 그대로 두고, 초기화가 필요한 컬렉션들을 모아 IN 조건 쿼리 하나로 가져오는 방식입니다. Hibernate의 default_batch_fetch_size나 @BatchSize로 켭니다.

문제는 쿼리 한 번의 느림이 아니라 횟수입니다 — 쿼리 하나하나는 빠르지만 DB와 네트워크를 N번 왕복하면 합쳐서 느려집니다. 데이터가 적은 개발 환경에서는 드러나지 않습니다.
원인은 지연 로딩이 반복문 안에서 쓰이는 것입니다 — 부모 목록을 읽은 뒤 각 부모의 연관 데이터에 접근하는 순간마다 쿼리가 나갑니다.
해결 방향은 로딩을 한꺼번에 하는 것입니다 — 조인으로 같은 쿼리에 싣거나(join fetch, @EntityGraph), IN으로 묶어 한 번에 가져옵니다(batch fetch). 필요한 컬럼만 DTO로 바로 조회하는 방법도 있습니다.
페이징이 필요한 컬렉션 연관에는 배치 페치가 대안이 됩니다 — 컬렉션 조인 페치에 페이징을 걸면 DB가 아니라 메모리에서 자르게 되고(Hibernate 7.3 이하), 컬렉션 여러 개를 한 번에 조인하기도 어렵습니다. 가능하면 조인 페치나 DTO 조회가 더 낫다는 것이 Hibernate 문서의 입장입니다.
이 시각화에서 확인할 것 — "N+1 발생" 탭에서 쿼리 횟수가 1 + 5로 늘어나는 과정을, "조인 페치" 탭에서 쿼리 1번과 페이징 경고를, "IN 일괄 조회" 탭에서 쿼리가 2번으로 줄어드는 과정을 STEP으로 확인하세요.

배경

객체지향 언어의 객체 그래프와 관계형 데이터베이스의 테이블 사이에는 구조 차이가 있습니다. 객체에서는 team.getMembers()처럼 참조를 따라가면 되지만, 데이터베이스에서는 그 순간마다 조회 쿼리가 필요합니다. ORM은 이 차이를 숨겨 편리함을 주는 대신, 객체 탐색 한 번이 쿼리 한 번으로 바뀌는 비용을 코드에서 보이지 않게 만듭니다. Jakarta Persistence(JPA) 명세는 연관의 기본 로딩 방식과 fetch 전략을 정하고, Hibernate 같은 구현체가 그에 맞춰 SQL을 만듭니다. N+1은 Hibernate, Rails, MyBatis 같은 여러 ORM과 매퍼의 문서에서 같은 이름으로 다루는 고전적인 성능 문제입니다.

숫자로 확인하기

쿼리 수 — 팀 N개의 멤버를 지연 로딩으로 읽으면 쿼리는 1 + N번입니다. 팀 5개는 6번, 100개는 101번, 1,000개는 1,001번입니다.
조인 페치 — 쿼리는 1번이지만 결과 행 수는 멤버 수와 멤버 없는 팀 수(팀마다 1행)의 합입니다. 모든 팀에 멤버가 있고 멤버가 모두 15명이면 15행이 돌아옵니다.
배치 페치 — 쿼리는 1 + ⌈N ÷ 배치 크기⌉번 근처입니다. 배치 크기가 100이면 팀 100개도 2번입니다. 배치 크기는 한 번에 묶어 가져오는 키(id)의 최대 개수입니다.
컬렉션 연관이 둘 이상일 때 — 조인 페치로 인덱스 컬럼이 없는 List(bag) 컬렉션 두 개를 동시에 가져오면 Hibernate가 MultipleBagFetchException을 던집니다. bag은 중복 요소를 허용해, 두 개를 조인하면 곱해진 행과 실제 중복을 구분할 수 없기 때문입니다. Set으로 바꾸면 예외는 피하지만 행이 곱해지는 문제는 남습니다.

자주 하는 오해

즉시 로딩(EAGER)으로 바꾸면 해결된다 — JPQL로 목록을 조회하면 연관 엔티티를 가져오는 쿼리가 항목마다(서로 다른 연관 엔티티 수만큼) 따로 나가는 모양은 그대로입니다. 오히려 필요 없는 곳에서도 연관 데이터를 읽게 되어 문제가 넓어집니다.
모든 곳에 join fetch를 쓰면 된다 — 컬렉션 조인 페치는 페이징과 함께 쓰면(Hibernate 7.3 이하) DB가 아니라 메모리에서 자르게 되어 데이터가 많을 때 위험하고, 결과 행이 부풀어 오히려 느릴 수 있습니다.
JPA를 쓰지 않으면 N+1이 없다 — MyBatis에서도 연관 데이터를 건별 select로 불러오면 같은 문제가 생기고, MyBatis 문서가 이를 N+1 Selects Problem이라 부릅니다. ORM이 쉽게 만들 뿐 원리는 같습니다.
쿼리가 많으면 인덱스가 없어서 느린 것이다 — 각 쿼리가 인덱스를 잘 타도 쿼리가 N번 나가면 왕복 비용이 N번 쌓입니다. N+1은 쿼리 하나의 속도가 아니라 횟수의 문제입니다.

면접에서 이렇게 물어요

면접 질문

N+1 문제란 무엇이고 왜 생기나요?

목록을 1번 조회한 뒤 각 항목의 연관 데이터를 가져오는 쿼리가 항목 수 N번 추가로 실행되는 현상입니다. 지연 로딩된 연관에 반복문에서 접근하거나, 즉시 로딩인데 JPQL로 조회할 때 생깁니다.

면접 질문

해결 방법과 각각의 단점은?

join fetch와 @EntityGraph는 연관을 한 번에 로딩해 쿼리를 줄이지만 컬렉션이면 행이 부풀어 오르고, 컬렉션 join fetch에 페이징을 걸면 DB가 아니라 메모리에서 일어납니다. 배치 페치는 쿼리가 몇 번 더 나가지만 페이징과 여러 컬렉션에 안전합니다. 화면에 필요한 값만 DTO로 조회하는 방법도 있습니다.

면접 질문

컬렉션 join fetch에 페이징을 쓰면 어떻게 되나요?

조인 결과의 행 수가 부모 수와 달라 DB의 limit으로 부모 단위로 자를 수 없습니다. Hibernate 7.3 이하는 경고를 남기고 모든 행을 메모리로 읽은 뒤 메모리에서 페이징하므로 데이터가 많으면 메모리 문제가 생깁니다. 7.4부터는 DB가 지원하면 SQL에서 처리하도록 바뀌었습니다.

면접 질문

N+1이 생겼는지 어떻게 확인하나요?

SQL 로그에서 같은 모양의 쿼리가 반복되는지 봅니다. generate_statistics를 켜고 Hibernate Statistics의 getPrepareStatementCount로 실행된 쿼리 수를 세거나, 테스트에서 쿼리 횟수를 단언하면 재발을 막을 수 있습니다.

실제 시스템에서는

Spring Data JPA — 쿼리 메서드에 @EntityGraph(attributePaths = ...)를 붙이거나 @Query에 join fetch를 써서 연관을 함께 로딩합니다. 프로젝트 전역으로는 spring.jpa.properties.hibernate.default_batch_fetch_size를 설정해 둡니다.
SQL 로그 확인 — logging.level.org.hibernate.SQL=DEBUG로 실행되는 SQL을 로그에 남길 수 있고, 개발 중에 같은 쿼리가 줄줄이 찍히는지 보는 것이 가장 빠른 점검입니다.
조회 전용 API — 목록 화면처럼 읽기만 하는 곳은 엔티티 대신 필요한 컬럼만 DTO 프로젝션으로 조회해 연관 로딩 문제를 아예 피하기도 합니다.
다른 ORM — Django의 select_related와 prefetch_related, Rails의 includes처럼 이름은 달라도 연관 데이터를 미리 가져오는 같은 장치를 제공합니다.

함께 보면 좋은 토픽

SQL JOIN — join fetch가 쿼리에 싣는 조인이 어떤 결과 행을 만드는지 봅니다.
인덱스 — 쿼리가 아무리 빨라도 횟수가 많으면 느려지는 것과 대비해 한 쿼리를 빠르게 하는 방법을 봅니다.
실행 계획 — 개별 쿼리가 어떻게 실행되는지 확인하는 방법을 봅니다.
커넥션 풀 — N+1처럼 쿼리가 많을 때 커넥션을 오래 점유하는 문제와 연결해 봅니다.
