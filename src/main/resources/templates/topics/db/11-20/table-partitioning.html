테이블 파티셔닝

태그

테이블 파티셔닝은 논리적으로 하나인 큰 테이블을 파티션 키 기준으로 더 작은 물리 조각(파티션)으로 나누어 저장하는 방법입니다. 응용 프로그램은 여전히 테이블 하나를 조회하지만, 데이터베이스는 행을 키 값에 맞는 파티션에 넣고, WHERE에 파티션 키 조건이 있으면 조회할 때 필요한 파티션만 읽습니다.

PostgreSQL 문서는 파티셔닝의 이점으로 자주 쓰는 행이 한두 파티션에 모여 있을 때의 조회 성능, 파티션을 붙이고 떼는 방식으로 하는 대량 적재와 삭제, 잘 쓰지 않는 데이터의 저렴한 저장소 이동을 듭니다. 이 토픽에서는 Range, List, Hash 세 분할 방식, 파티션 프루닝, 파티셔닝과 샤딩의 차이를 시각화로 확인합니다.

핵심 개념

파티션과 파티션 키

테이블을 나누는 기준 열이 파티션 키이고, 나뉜 조각 하나하나가 파티션입니다. 행은 키 값에 따라 어느 파티션에 들어갈지 정해집니다.

핵심 개념

Range 파티셔닝

키 값의 범위로 나눕니다. 범위끼리는 겹치지 않고, 날짜나 시간처럼 이어지는 값에 잘 맞습니다.

핵심 개념

List 파티셔닝

키 값이 어느 값 목록에 속하는지로 나눕니다. 국가나 상태 코드처럼 값이 몇 가지로 정해진 열에 맞습니다.

핵심 개념

Hash 파티셔닝

키 값의 해시를 modulus로 나눈 나머지로 나눕니다(보통 파티션 수와 같게 둡니다). 행이 비교적 고르게 흩어지지만 키의 범위로 파티션을 골라내기는 어렵습니다.

핵심 개념

파티션 프루닝

WHERE 조건을 보고 읽을 필요가 없는 파티션을 계획 수립 또는 실행 중에 제외하는 최적화입니다. 파티션 키 열을 단순하게 비교하는 조건이 있을 때 가장 잘 동작합니다.

핵심 개념

파티셔닝과 샤딩

파티셔닝은 보통 한 데이터베이스 안에서 테이블을 나누고, 샤딩은 데이터를 여러 서버에 나눠 저장합니다.

조회가 필요한 파티션만 읽습니다 — WHERE에 파티션 키 조건이 있으면 나머지 파티션은 계획에서 빠져 읽을 데이터가 줄어듭니다.
오래된 데이터를 통째로 지웁니다 — 기간별 Range 파티션이면 보관 기간이 지난 파티션을 떼어 내 삭제할 수 있어, 행마다 지우는 대량 DELETE의 부담을 피합니다.
키 선택이 성능을 좌우합니다 — 자주 쓰는 WHERE 조건과 맞지 않는 열로 나누면 모든 파티션을 훑게 되어 프루닝의 이점을 얻지 못합니다.
제약 조건에 제한이 있습니다 — PostgreSQL에서 파티션된 테이블의 기본 키와 유니크 제약에는 파티션 키 열이 모두 들어 있어야 합니다. 각 파티션의 인덱스는 자기 파티션 안에서만 유일성을 강제하기 때문입니다.
이 시각화에서 확인할 것 — "분할 방식" 탭에서 같은 24행이 Range, List, Hash로 달리 나뉘는 모습을, "파티션 프루닝" 탭에서 month 조건이면 파티션 하나만 읽고 region 조건이면 4개를 모두 읽는 모습을, "파티셔닝과 샤딩" 탭에서 한 서버 안의 파티션과 여러 서버의 샤드가 어떻게 다른지 STEP으로 확인하세요.

파티셔닝의 배경

테이블이 서버 메모리보다 클 정도로 매우 커지면 인덱스가 커지고 정리 작업이 오래 걸리며, 보관 기간이 지난 데이터를 지우는 일 자체가 부담이 됩니다. 한 테이블을 나눠서 다루면 이런 작업을 조각 단위로 할 수 있습니다.

PostgreSQL은 10 버전부터 PARTITION BY로 Range와 List를 선언하는 선언적 파티셔닝을 제공하고, 11 버전에서 Hash 파티셔닝이 추가되었습니다. MySQL도 RANGE, LIST, HASH, KEY 같은 파티셔닝을 지원합니다. 구체적인 문법과 제약은 데이터베이스마다 다르고, MySQL도 모든 유니크 키가 파티셔닝에 쓰는 열을 포함해야 합니다.

숫자로 확인하기

Range 4개 — 주문 24행을 month로 나누면 1월부터 4월까지 6, 5, 7, 6행입니다. 파티션 크기가 달라도 합은 항상 24행입니다.
List와 Hash — region으로 나누면 KR 12행, US 8행, JP 4행으로 고르지 않고, id % 4로 나누면 6행씩 고릅니다.
프루닝 효과 — month = 3으로 찾으면 파티션 1개 7행만 검사하고, month가 2에서 3 사이면 파티션 2개 12행을 검사합니다. 파티션 키가 아닌 region으로 찾으면 파티션 4개 24행을 모두 검사합니다.
코드 확인 — 파이썬과 자바 모델 모두 Range 배정이 6, 5, 7, 6행이고 해시 배정이 6행씩이며, 파이썬 scan은 키 조건이면 7행, 키가 아니면 24행을 반환합니다.

자주 하는 오해

파티션을 나누면 모든 조회가 빨라진다 — WHERE에 파티션 키 조건이 있어 프루닝이 될 때 이점이 큽니다. 키 조건이 없으면 모든 파티션을 읽고, 파티션 수가 많으면 계획 수립 비용이 늘 수 있습니다.
파티션은 많을수록 좋다 — 파티션이 지나치게 많으면 계획 수립 시간과 메모리 사용이 늘어납니다. 필요한 만큼만 나누며, PostgreSQL 문서는 테이블이 아주 클 때에만 보통 이득이 있다고 설명합니다.
파티셔닝과 샤딩은 같은 말이다 — 파티셔닝은 보통 한 데이터베이스 안에서 테이블을 나누는 것이고, 샤딩은 데이터를 여러 서버에 나눠 저장하는 것입니다.
인덱스를 대신해 준다 — 파티셔닝은 읽을 범위를 줄일 뿐이어서, 파티션 안에서 일부 행만 읽는 쿼리에는 인덱스가 여전히 도움이 됩니다. 파티셔닝이 인덱스를 완전히 대체하지는 않습니다.
키 열에 함수를 씌워도 프루닝이 된다 — 프루닝은 키 열을 상수나 파라미터와 단순 비교할 때 가장 확실합니다. 키 열에 함수를 씌우거나 복잡한 식과 비교하면 파티션을 거르지 못할 수 있습니다.
어떤 열이든 키로 쓸 수 있다 — 키는 자주 쓰는 WHERE 조건과 보관 정책에 맞춰 골라야 하고, 파티션된 테이블의 기본 키와 유니크 제약은 키 열을 포함해야 하는 제약도 있습니다.

면접 질문

Range 파티셔닝의 대표적인 예는?

날짜 범위로 나누는 경우입니다. 월별이나 연도별 파티션으로 나누면 오래된 기간을 파티션 단위로 보관하거나 삭제하기 쉽습니다.

면접 질문

파티션 프루닝이란?

WHERE 조건으로 읽을 필요가 없는 파티션을 계획 수립 또는 실행 중에 제외하는 최적화입니다. 파티션 키 조건이 있어야 동작합니다.

면접 질문

파티셔닝과 샤딩은 어떻게 다른가요?

파티셔닝은 보통 한 데이터베이스 인스턴스 안에서 테이블을 나누고, 샤딩은 데이터를 여러 서버에 나눠 저장합니다. 샤딩은 서버를 늘려 용량과 처리량을 키울 수 있지만 라우팅과 샤드 간 조인 같은 부담이 따릅니다.

면접 질문

파티션 키는 어떻게 고르나요?

자주 쓰는 WHERE 조건과 데이터 보관 정책에 맞는 열을 고릅니다. 시간 기반 데이터는 날짜 열을 Range 키로 쓰는 경우가 많습니다.

활용 분야

로그와 이벤트 테이블 — 시간 순으로 쌓이는 데이터를 월별이나 일별 Range 파티션으로 나누고, 보관 기간이 지난 파티션을 삭제합니다.
주문과 거래 이력 — 최근 기간 조회가 대부분이면 기간 키로 나눠 최근 파티션만 읽게 합니다.
지역이나 상태별 분리 — 국가 코드처럼 값이 정해진 열은 List 파티셔닝으로 나눠 해당 지역 조회와 관리를 분리합니다.

함께 보면 좋은 토픽

샤딩 — 데이터를 여러 서버에 나누는 방식과 파티셔닝의 차이를 봅니다.
인덱스 — 파티션 안에서 행을 빨리 찾는 방법을 봅니다.
쿼리 실행 계획 — EXPLAIN으로 프루닝된 파티션을 확인하는 방법을 봅니다.
복제 — 데이터를 다른 서버에 복사하는 또 다른 확장 방식입니다.
