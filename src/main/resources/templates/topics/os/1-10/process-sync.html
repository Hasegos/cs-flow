프로세스 동기화

태그

여러 프로세스·스레드가 공유 자원에 동시에 접근하면 Race Condition이 발생합니다. 프로세스 동기화는 임계 구역(Critical Section)을 보호해 실행 순서와 무관하게 항상 올바른 결과를 보장하는 기법입니다. Mutex와 Semaphore가 대표적인 해결 도구입니다.

핵심 개념

임계 구역 (Critical Section)

공유 자원에 접근하는 코드 구간입니다. 올바른 동기화는 상호 배제(Mutual Exclusion) · 진행(Progress) · 한정 대기(Bounded Waiting) 세 조건을 모두 만족해야 합니다.

핵심 개념

Race Condition

둘 이상의 스레드가 공유 자원을 동시에 읽고 쓸 때 실행 순서에 따라 결과가 달라지는 현상입니다. counter++ 같은 비원자적 연산이 대표적인 발생 지점입니다.

핵심 개념

Mutex (상호 배제 락)

한 번에 하나의 스레드만 Lock을 획득하고 임계 구역에 진입할 수 있습니다. 일반적으로 Lock을 보유한 스레드가 Unlock합니다(Java의 ReentrantLock은 락을 갖지 않은 스레드가 풀려 하면 예외를 던집니다). 소유권(Ownership) 개념이 있어 이진 Semaphore와 구별됩니다.

핵심 개념

Semaphore

정수 카운터(S)로 자원 접근을 제어합니다. wait(P): S가 0이면 블로킹, 0 초과면 S-- 후 진입. signal(V): S++하여 대기 중인 프로세스를 깨웁니다. 이진(0/1)과 계수형(N)으로 나뉩니다.

핵심 개념

Monitor

상호 배제와 조건 동기화를 언어 레벨에서 제공하는 고수준 추상화입니다. Java의 synchronized + wait()/notify()가 대표적인 예이며, Python에서는 threading.Condition이 이에 대응합니다(단순 with Lock은 상호 배제만 제공). 내부적으로 Mutex + Condition Variable로 구성됩니다.

핵심 개념

Spinlock vs Blocking

Spinlock은 Lock이 해제될 때까지 CPU를 점유하며 바쁜 대기(Busy Waiting)합니다. 컨텍스트 스위치 비용이 없어 짧은 대기에 유리하고, 멀티코어에서 의미가 있습니다. Blocking은 스레드를 Sleep 시켜 CPU를 양보하므로 긴 대기에 적합합니다.

상호 배제 (Mutual Exclusion) — 임계 구역에는 한 번에 하나의 프로세스만 진입해야 합니다. 동기화 메커니즘이 보장해야 하는 가장 기본 조건입니다.
Deadlock 위험 — Mutex 두 개를 서로 다른 순서로 획득하면 교착 상태가 발생합니다. Lock 획득 순서를 전역적으로 통일하거나, tryLock + timeout 패턴으로 방지합니다.
메모리 가시성 (Visibility) — 한 스레드의 쓰기가 다른 스레드에 즉시 보이지 않을 수 있습니다. Java의 volatile, C의 memory barrier(fence)로 가시성과 CPU·컴파일러의 재정렬을 제어합니다.
생산자-소비자 문제 — Semaphore의 대표 응용. empty(N)·full(0) 두 Semaphore와 mutex(1) 하나를 조합해 버퍼 크기 제한과 상호 배제를 동시에 해결합니다.
CAS (Compare-And-Swap) — 하드웨어 원자 명령어로 락 없이 공유 변수를 안전하게 갱신합니다. Java의 AtomicInteger는 락 없는 스레드 안전 연산을 제공하고, GCC에는 __atomic_compare_exchange 내장 함수가 있습니다. Lock-Free 알고리즘의 기반입니다.

왜 동기화가 필요한가

여러 스레드나 프로세스가 같은 데이터를 동시에 바꾸면 실행 순서에 따라 결과가 달라질 수 있습니다. 동기화는 이런 접근의 순서를 통제해 결과를 항상 같게 만드는 일입니다. 상호 배제 문제는 1960년대에 Dijkstra의 논문 'Solution of a Problem in Concurrent Programming Control'(1965) 등으로 연구되었고, 세마포어도 Dijkstra가 제안한 도구로 알려져 있습니다.

숫자로 확인하기

출금 경쟁 — 잔액이 100원일 때 두 스레드가 동시에 30원씩 출금합니다. 둘 다 100을 읽고 각자 70을 저장하면 결과는 70원입니다. 순서대로 처리했다면 40원이어야 합니다.
세마포어 값 따라가기 — 자원이 2개라서 S = 2로 시작하면 wait 한 번에 S는 1, 두 번째 wait에 0이 됩니다. 세 번째 wait는 S가 0이라서 블로킹되고, 누군가 signal을 호출할 때 풀립니다.
생산자-소비자(버퍼 5칸) — empty = 5, full = 0, mutex = 1로 시작합니다. 생산자가 3개를 넣으면 empty는 2, full은 3이 되고, 소비자가 1개를 꺼내면 empty는 3, full은 2가 됩니다. empty가 0이면 생산자가, full이 0이면 소비자가 기다립니다.
임계 구역의 비용 — 작업 시간 중 락으로 보호한 임계 구역이 10%라면 이 부분은 한 번에 하나만 실행하므로, 코어를 아무리 늘려도 속도 향상은 최대 10배입니다. 임계 구역은 짧게 둘수록 좋습니다.

자주 하는 오해

volatile이면 count++도 안전하다 — Java의 volatile은 다른 스레드에 쓰기가 보이게 하고 순서를 정할 뿐, 읽기-더하기-쓰기를 하나의 원자 연산으로 만들지 않습니다. 원자성은 synchronized, 락, AtomicInteger 같은 도구가 줍니다.
Mutex와 이진 세마포어는 같다 — 둘 다 0과 1처럼 쓸 수 있지만 뮤텍스는 락을 잡은 스레드가 풀어야 하고, 세마포어는 다른 스레드가 signal을 호출할 수 있어 신호 전달 용도로도 쓰입니다.
Python은 GIL이 있어서 경쟁 상태가 없다 — GIL은 인터프리터 내부를 보호할 뿐, i = i + 1 같은 여러 단계 연산이 중간에 끊기는 것은 막지 않습니다. 필요하면 threading.Lock을 씁니다.
락을 많이 걸수록 안전하다 — 락이 많거나 범위가 넓으면 성능이 떨어지고 교착 상태가 생길 위험도 커집니다. 보호할 데이터와 범위를 정확히 잡아야 합니다.

면접에서 이렇게 물어요

면접 질문

임계 구역 문제의 해결 조건 세 가지는 무엇인가요?

상호 배제는 한 번에 하나만 들어가는 것, 진행은 들어갈 수 있는데도 아무도 못 들어가는 일이 없게 하는 것, 한정 대기는 기다리는 시간에 상한이 있어 기아가 없게 하는 것입니다.

면접 질문

Mutex와 Semaphore는 어떻게 다른가요?

Mutex는 상호 배제를 위한 락으로 잡은 스레드가 소유자가 되어 풀어야 합니다. Semaphore는 카운터로 동시에 접근할 수 있는 수를 제한하거나 스레드 사이에 신호를 전달하는 데 쓰고 소유자 개념이 없습니다.

면접 질문

Spinlock은 언제 쓰나요?

락을 기다리는 동안 CPU를 쓰며 반복 확인하므로, 기다리는 시간이 컨텍스트 스위치 비용보다 짧을 때 유리하고 멀티코어에서 의미가 있습니다. 대기가 길면 스레드를 재우는 블로킹 락이 낫습니다.

면접 질문

락 없이 동기화할 수 있나요?

하드웨어가 제공하는 원자 명령인 CAS로 값을 비교하고 바꾸는 락 프리 방식이 있습니다. Java의 AtomicInteger가 대표적이고, 실패하면 다시 시도하는 반복이 필요합니다.

실제 시스템에서는

Java의 도구 — Java는 synchronized, ReentrantLock, java.util.concurrent.atomic 패키지를 제공합니다. 메모리 가시성과 happens-before 규칙은 Java 언어 명세 17장이 정의합니다.
POSIX 뮤텍스 — pthread_mutex_lock은 POSIX 표준이 정의하며, 소유하지 않은 뮤텍스를 푸는 동작은 뮤텍스 종류에 따라 정의가 달라집니다.
futex — futex(2) 매뉴얼은 리눅스의 futex가 빠른 사용자 공간 락의 바탕이 되는 시스템 콜이라고 설명합니다. 경쟁이 없을 때는 시스템 콜 없이 처리하고 기다려야 할 때만 커널의 도움을 받는 구조입니다.
