가상 메모리

태그

가상 메모리는 실제 물리 메모리보다 더 큰 주소 공간을 프로세스에 제공하는 기법입니다. 필요한 페이지만 물리 메모리에 올리고(Demand Paging), 부족하면 교체 알고리즘으로 어떤 페이지를 내보낼지 결정합니다.

핵심 개념

요구 페이징 (Demand Paging)

프로세스 실행 시 모든 페이지를 메모리에 올리지 않고, 실제 접근할 때만 적재합니다. 페이지 폴트(Page Fault)가 발생하면 OS가 디스크에서 해당 페이지를 읽어옵니다.

핵심 개념

FIFO (First-In, First-Out)

가장 먼저 적재된 페이지를 교체합니다. 구현이 단순하지만 프레임 수를 늘려도 폴트가 증가하는 Belady's Anomaly가 발생할 수 있습니다.

핵심 개념

LRU (Least Recently Used)

가장 오랫동안 사용되지 않은 페이지를 교체합니다. 최근 사용 기록을 기반으로 미래를 예측합니다. 구현 비용이 높지만 실용적으로 좋은 성능을 보입니다.

핵심 개념

Optimal (OPT)

앞으로 가장 오랫동안 사용되지 않을 페이지를 교체합니다. 미래를 알아야 하므로 실제 구현 불가능하지만 다른 알고리즘 성능 비교의 기준(가장 적은 폴트를 내는 이상적인 알고리즘)이 됩니다.

핵심 개념

스래싱 (Thrashing)

프로세스가 페이지 교체에만 시간을 쏟아 실제 작업을 못하는 현상입니다. 물리 메모리 프레임 수가 프로세스의 워킹셋(Working Set)보다 작을 때 발생합니다.

핵심 개념

워킹셋 (Working Set)

특정 시간 윈도우 내에 프로세스가 참조한 페이지 집합입니다. 워킹셋 크기만큼 프레임이 확보되면 폴트율이 급격히 낮아집니다. 지역성(Locality) 원리를 기반으로 합니다.

Belady's Anomaly — FIFO에서 프레임 수를 늘렸는데 오히려 페이지 폴트가 증가하는 현상입니다. LRU·OPT는 이 현상이 없는 것으로 알려져 있으며 스택 알고리즘(Stack Algorithm)으로 분류됩니다.
Copy-on-Write (CoW) — fork() 시 부모·자식이 같은 물리 페이지를 공유하다가 쓰기 발생 시점에만 복사합니다. 불필요한 복사를 줄여 fork() 비용을 낮춥니다.
페이지 폴트 처리 순서 — ① MMU가 유효 비트 확인 → ② OS 트랩 → ③ 빈 프레임 확인 → ④ (빈 프레임이 없으면) 교체 알고리즘 선택 → ⑤ 디스크 I/O → ⑥ 페이지 테이블 갱신 → ⑦ 프로세스 재개. 디스크 I/O가 포함되어 메모리 접근보다 훨씬 오래 걸립니다(HDD는 밀리초 단위).
Clock 알고리즘 (Second Chance) — FIFO의 변형으로 참조 비트(R)를 추가합니다. 교체 대상이 R=1이면 R을 0으로 바꾸고 기회를 한 번 더 줍니다. LRU를 근사하는 구현입니다.

가상 메모리가 주는 것

가상 메모리는 프로세스마다 크고 연속된 자신만의 주소 공간을 주고, 실제로 쓰는 페이지만 물리 메모리에 올리는 기법입니다. 덕분에 프로세스끼리 서로의 메모리를 볼 수 없고, 물리 메모리보다 큰 프로그램도 실행할 수 있으며, 같은 물리 페이지를 여러 프로세스가 공유할 수도 있습니다. 주소 변환의 기본은 메모리 관리 토픽에서 다룹니다.

숫자로 확인하기

Belady의 모순 예제 — 참조 열이 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5일 때 FIFO는 프레임 3개에서 페이지 폴트가 9번, 프레임 4개에서 10번입니다. 프레임을 늘렸는데 폴트가 늘었습니다.
같은 열에서 알고리즘 비교 — 프레임 3개 기준으로 FIFO 9번, LRU 10번, OPT 7번이고 프레임 4개에서는 FIFO 10번, LRU 8번, OPT 6번입니다. 이 열에서 LRU와 OPT는 프레임이 늘면 폴트가 줄어듭니다. 이 열에서는 3개일 때 LRU가 FIFO보다 나쁩니다.
페이지 폴트가 평균 접근 시간에 미치는 영향(가정) — 메모리 접근 200ns, 폴트 처리 8ms(8,000,000ns)로 가정하면 평균 접근 시간은 (1 − p) × 200 + p × 8,000,000입니다. p가 1/1,000이면 199.8 + 8,000 = 약 8,200ns로 약 41배 느려집니다.
성능 저하를 10% 이내로 막으려면 — 같은 가정에서 평균 접근 시간을 220ns 이하로 두려면 p × (8,000,000 − 200) ≤ 20이라서 p는 약 0.0000025, 곧 접근 약 400,000번에 폴트 한 번 이하여야 합니다.

자주 하는 오해

가상 메모리는 디스크를 메모리처럼 쓰는 기능이다 — 디스크 스왑은 가상 메모리를 구현하는 수단 중 하나이고, 가상 메모리의 본질은 프로세스별 주소 공간의 추상화와 격리입니다.
페이지 폴트는 오류다 — 요구 페이징에서는 정상 동작입니다. 리눅스는 디스크 I/O가 필요한 major fault와 필요 없는 minor fault를 구분하며 getrusage(2)가 두 횟수를 알려 줍니다.
프레임을 늘리면 폴트는 항상 줄어든다 — FIFO는 Belady의 모순으로 늘 수 있습니다. 위 예제가 그 사례입니다.
스왑을 쓰면 항상 문제다 — 거의 쓰이지 않는 페이지를 내보내 메모리를 확보하는 것은 정상입니다. 문제는 자주 쓰는 페이지가 계속 오가는 스래싱입니다.

면접에서 이렇게 물어요

면접 질문

가상 메모리가 왜 필요한가요?

프로세스마다 독립된 주소 공간으로 보호와 격리를 주고, 물리 메모리보다 큰 프로그램을 실행하게 하며, 필요한 페이지만 올려 메모리를 효율적으로 씁니다. 프로그램이 물리 메모리 배치를 신경 쓰지 않아도 됩니다.

면접 질문

페이지 폴트가 났을 때 어떤 일이 일어나나요?

MMU가 유효하지 않은 항목을 발견해 운영체제로 트랩합니다. 운영체제가 접근이 유효한지 확인하고, 빈 프레임을 찾거나 교체 알고리즘으로 희생 페이지를 정한 뒤 디스크에서 페이지를 읽어 페이지 테이블을 고치고 명령을 다시 실행합니다.

면접 질문

스래싱은 무엇이고 어떻게 해결하나요?

프로세스가 필요한 프레임을 얻지 못해 폴트와 교체만 반복하는 상태입니다. 워킹셋을 기준으로 프레임을 배분하고, 동시에 실행하는 프로세스 수를 줄이거나 메모리를 늘려 해결합니다.

면접 질문

LRU는 어떻게 구현하나요?

정확한 LRU는 접근마다 순서를 갱신해야 해서 비용이 큽니다. 그래서 참조 비트를 쓰는 Clock 같은 근사 알고리즘을 씁니다.

실제 시스템에서는

메모리 상태 보기 — /proc/meminfo는 시스템 전체 메모리와 스왑 사용량을, /proc/PID/status의 VmSize와 VmRSS는 프로세스의 가상 크기와 실제 올라온 크기를 보여 줍니다(proc_meminfo(5), proc_pid_status(5) 매뉴얼).
스왑 성향 조절 — 커널 문서는 vm.swappiness를 스왑 I/O와 파일시스템 페이징의 상대적 비용을 나타내는 값(0~200)으로 설명하며, 값에 따라 페이지 캐시와 스왑 대상 페이지에 가하는 회수 압박의 비중이 달라집니다.
LRU 근사 — 커널 문서는 페이지 회수를 개선하는 LRU 구현인 다세대(multi-gen) LRU 기능을 설명합니다.
