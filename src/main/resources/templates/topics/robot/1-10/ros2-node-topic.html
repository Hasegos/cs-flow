ROS2 노드와 토픽(발행·구독)

태그

로봇 한 대에는 카메라, 라이다, 바퀴 모터, 경로 계획, 지도 작성처럼 서로 다른 일을 하는 프로그램이 동시에 돌아갑니다. 이 프로그램들이 하나의 거대한 코드가 아니라 각자 독립적으로 만들어지고 데이터를 주고받으려면 공통의 통신 규칙이 필요합니다. ROS 2(Robot Operating System 2)는 이름과 달리 운영체제가 아니라 로봇 소프트웨어를 위한 미들웨어와 도구 모음이고, 그 통신의 가장 기본이 노드(node)와 토픽(topic)입니다.

이 토픽에서는 라이다 노드가 /scan 토픽으로 측정값을 발행하고 SLAM 노드가 구독하는 예로, 발행자와 구독자가 만나는 과정, 한 토픽에 여러 노드가 붙는 구조와 타입이 맞지 않을 때의 문제, 구독자가 느릴 때 큐에서 메시지가 버려지는 모습을 단계별로 봅니다.

핵심 개념

노드(node)

하나의 논리적인 일을 맡은 계산 단위입니다. 라이다 드라이버, 지도 작성, 모터 제어처럼 역할별로 노드를 나누고, 노드끼리 토픽 · 서비스 · 액션으로 통신합니다.

핵심 개념

토픽(topic)

이름이 붙은 데이터 통로입니다. 발행자가 메시지를 내보내고 구독자가 받는 단방향 통신이며, 센서 값처럼 계속 흘러가는 데이터에 맞습니다.

핵심 개념

메시지(message)

토픽으로 오가는 데이터의 형식입니다. sensor_msgs/msg/LaserScan처럼 .msg 파일로 필드를 정의하고, 토픽마다 하나의 메시지 타입을 가집니다.

핵심 개념

발행자와 구독자

publisher는 토픽에 메시지를 보내고 subscription은 콜백 함수로 받습니다. 한 노드가 여러 토픽의 발행자와 구독자를 동시에 가질 수 있습니다.

핵심 개념

DDS와 디스커버리

ROS 2는 데이터 전달에 DDS 표준 기반의 미들웨어를 씁니다. 같은 토픽 이름과 타입을 가진 발행자와 구독자를 디스커버리로 자동으로 찾아 연결합니다.

핵심 개념

큐 크기(depth)

발행자와 구독자가 메시지를 임시로 쌓아 두는 크기입니다. 구독자가 처리하는 속도보다 메시지가 빨리 오면 큐가 차고, 가득 차면 오래된 메시지부터 버려집니다.

노드를 작게 나누는 것이 ROS의 기본 설계입니다 — 기능마다 노드를 분리하면 센서나 알고리즘을 갈아 끼우고 노드 하나만 따로 시험하기 쉽습니다.
토픽은 발행자와 구독자를 느슨하게 연결합니다 — 서로를 직접 알 필요가 없고 응답도 없어서, 구독자를 추가하거나 빼도 발행자 코드는 바뀌지 않습니다.
연결 조건은 이름과 타입, 그리고 QoS 호환입니다 — 이름이 같아도 메시지 타입이 다르면 연결되지 않습니다. QoS는 다음 토픽(DDS QoS)에서 자세히 봅니다.
토픽은 연속 데이터에, 요청과 응답은 서비스와 액션에 — 센서 스트림 같은 흐름은 토픽으로, 한 번 요청하고 결과를 받는 일은 서비스나 액션으로 나눕니다.
이 시각화에서 확인할 것 — "발행 · 구독" 탭에서 발행자와 구독자가 서로를 찾고 콜백이 호출되는 흐름을, "여러 노드 연결" 탭에서 구독자와 발행자를 늘리는 과정과 타입 불일치를, "느린 구독자" 탭에서 큐가 가득 차 메시지가 버려지는 모습을 STEP으로 확인하세요.

배경

ROS는 2007년 11월 Willow Garage에서 PR2 로봇의 개발 환경으로 시작된 로봇 소프트웨어 프레임워크입니다. 초기 ROS 1은 중앙 마스터(ROS master)가 노드들의 연결을 중개했고, 연구용 로봇에 맞춰 설계돼 실시간성이나 여러 로봇 · 불안정한 네트워크 환경에서 한계가 있었습니다. 이를 보완해 만든 ROS 2는 통신 계층에 OMG가 표준화한 DDS를 기본 미들웨어로 채택해 마스터 없이 노드가 서로를 찾고, 통신 품질을 QoS로 조절할 수 있게 했습니다. 배포판은 해마다 나오며 장기 지원(LTS) 버전이 따로 있습니다.

숫자로 확인하기

공식 튜토리얼의 발행 주기 — 기본 발행자 예제는 타이머를 0.5초로 두어 초당 2번 메시지를 발행하고, create_publisher의 큐 크기는 10입니다.
기본 설정의 노드가 만드는 토픽 — 기본 설정의 노드는 /parameter_events와 /rosout 토픽을 만들어 ros2 topic list에 보입니다(노드 옵션으로 끌 수 있음). 각각 파라미터 변경 알림과 로그 메시지를 나르는 토픽입니다.
도메인 ID — 같은 네트워크에서 서로 다른 로봇 시스템이 섞이지 않게 ROS_DOMAIN_ID 환경 변수로 구분하며 기본값은 0입니다. 같은 도메인 ID의 노드끼리만 서로를 발견합니다. 공식 문서는 0부터 101까지를 안전한 범위로 안내하며, 이는 Linux 기본 포트 범위 기준이고 macOS와 Windows는 0~166까지입니다.
큐 손실 계산 — 큐 크기가 3인 구독자에 메시지가 5개 연달아 도착하고 콜백이 그동안 하나도 꺼내지 못하면 오래된 2개(1번, 2번)가 버려지고 3, 4, 5번만 남습니다.

자주 하는 오해

ROS는 로봇용 운영체제다 — 리눅스 같은 운영체제 위에서 도는 미들웨어와 라이브러리, 도구의 모음입니다. 이름에 운영체제가 들어 있을 뿐입니다.
토픽은 요청에 대한 응답을 준다 — 토픽은 한 방향 데이터 흐름이라 응답이 없습니다. 결과가 필요한 호출은 서비스나 액션입니다.
이름만 같으면 반드시 연결된다 — 메시지 타입이 같아야 하고 QoS 설정도 호환돼야 합니다. 맞지 않으면 연결이 만들어지지 않아 데이터가 오지 않습니다. rclcpp는 기본으로 경고 로그를 남기지만 rclpy는 이벤트 콜백을 직접 달기 전에는 아무 표시가 없을 수 있습니다.
구독을 시작하면 지난 메시지도 받는다 — 기본 설정에서는 구독이 연결된 이후에 발행된 메시지만 받습니다. 지난 값을 받으려면 발행자와 구독자 모두 QoS의 내구성(durability)을 Transient Local로 설정해야 합니다.

실제 시스템에서는

turtlesim 튜토리얼 — 공식 입문 예제에서 키보드 조종 노드가 /turtle1/cmd_vel 토픽에 geometry_msgs/msg/Twist 메시지를 발행하고, 거북이 노드가 구독해 움직입니다.
자율주행 스택 — Nav2 같은 내비게이션 프레임워크는 기본 설정에서 /scan(라이다), /odom(주행 거리), /cmd_vel(속도 명령) 같은 토픽으로 센서, 위치 추정, 경로 계획, 모터 제어 노드를 이어 붙입니다.
rosbag2 — ros2 bag record로 토픽의 메시지를 파일에 기록하고 나중에 재생해, 실제 로봇 없이 같은 센서 데이터로 알고리즘을 시험합니다.
ros2 CLI와 rqt — ros2 node list, ros2 topic list · echo · info · hz로 실행 중인 그래프를 조사하고, rqt_graph로 노드와 토픽의 연결을 그림으로 볼 수 있습니다.

함께 보면 좋은 토픽

멀티캐스트 · 브로드캐스트 — 노드가 서로를 찾는 디스커버리가 쓰는 네트워크 전송 방식을 봅니다.
TCP/IP 4계층 — DDS 통신이 올라가는 인터넷 프로토콜의 구조를 봅니다.
프로세스 — 노드는 보통 프로세스로 실행하지만 한 프로세스에 여러 노드를 넣을 수도 있습니다. 그 바탕이 되는 프로세스를 봅니다.
ROS2 서비스 vs 액션 — 토픽과 달리 요청 · 응답으로 동작하는 통신 방식을 봅니다.
DDS QoS — 발행자와 구독자의 연결 조건이 되는 통신 품질 설정을 봅니다.
