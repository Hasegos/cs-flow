로드 밸런서

태그

로드 밸런서는 들어오는 네트워크 트래픽을 여러 서버에 분산시켜 고가용성과 성능을 확보하는 장치입니다. 단일 서버 장애 시에도 서비스를 유지하고, 트래픽 폭증 시 수평 확장으로 대응합니다.

핵심 개념

Round Robin

요청을 서버 목록에 순서대로 순환 배분합니다. 구현이 단순하고 서버 성능이 동일할 때 효과적입니다. Weighted Round Robin은 서버 성능에 따라 가중치를 부여해 더 많은 요청을 보냅니다. 세션 유지가 필요 없는 무상태 서비스에 적합합니다.

핵심 개념

Least Connection

현재 활성 연결이 가장 적은 서버로 요청을 보냅니다. 요청 처리 시간이 다양할 때 효과적입니다. 긴 작업을 처리 중인 서버에 추가 부하가 쌓이는 것을 방지합니다. Weighted Least Connection은 서버 성능도 고려합니다.

핵심 개념

IP Hash

클라이언트 IP를 해시해 항상 같은 서버로 연결합니다. 세션 상태를 서버에 저장하는 경우 유용합니다. 같은 사용자가 항상 같은 서버에 접속해 세션 유지가 가능합니다. 단, 특정 IP에 트래픽이 집중되면 불균형이 발생할 수 있습니다.

핵심 개념

L4 vs L7 로드 밸런서

L4(전송 계층): TCP/UDP 포트와 IP 기반으로 분산합니다. 빠르고 단순하며 패킷 내용을 보지 않습니다. L7(응용 계층): HTTP 헤더, URL, 쿠키 등을 분석해 분산합니다. /api는 API 서버, /static은 파일 서버로 라우팅하는 콘텐츠 기반 분산이 가능합니다.

핵심 개념

헬스 체크

로드 밸런서는 주기적으로 서버 상태를 확인합니다. HTTP 헬스 체크는 /health 엔드포인트에 GET 요청을 보내 200 응답을 확인합니다. 서버가 응답하지 않으면 자동으로 풀에서 제외하고, 복구되면 자동으로 복귀합니다.

핵심 개념

세션 퍼시스턴스

Sticky Session이라고도 합니다. 같은 클라이언트의 요청을 항상 같은 서버로 보냅니다. 로드 밸런서가 발급하는 쿠키나 애플리케이션 쿠키(JSESSIONID 등), IP Hash 방식을 사용합니다. 단, 해당 서버 장애 시 세션이 손실되므로 Redis 같은 외부 세션 저장소 사용을 권장합니다.

Active-Passive vs Active-Active — Active-Passive는 평소엔 하나만 사용하고 장애 시 다른 하나로 전환합니다. Active-Active는 두 로드 밸런서가 동시에 트래픽을 처리합니다. Active-Active가 자원 활용률이 높지만 설정이 복잡합니다.
DSR (Direct Server Return) — 응답 트래픽이 로드 밸런서를 거치지 않고 클라이언트에 직접 전달됩니다. 응답이 요청보다 훨씬 큰 서비스(동영상 스트리밍 등)에서 로드 밸런서 병목을 줄일 수 있습니다. 요청은 LB를 거치지만 응답은 서버에서 직접 나갑니다. LVS의 Direct Routing 방식은 로드 밸런서와 서버가 같은 LAN 구간에 있어야 합니다.
nginx vs HAProxy — nginx는 HTTP(L7) 로드 밸런서로 정적 파일 서빙, SSL 종료, 캐싱도 겸하고, stream 모듈(기본 빌드에는 빠져 있어 --with-stream이 필요)로 TCP/UDP도 분산합니다. HAProxy는 TCP와 HTTP 로드 밸런싱을 모두 지원하는 전용 소프트웨어입니다. 클라우드에서는 AWS ALB/NLB, GCP Cloud Load Balancing을 사용합니다.

서버 한 대로는 부족한 이유

서버 한 대는 처리 용량에 한계가 있고, 그 한 대가 멈추면 서비스 전체가 멈춥니다. 같은 서버를 여러 대 두고 앞에 하나의 진입 주소를 세워 요청을 나누면 용량과 가용성을 함께 높일 수 있고, 이 진입점 역할이 로드 밸런서입니다. 서버를 늘려서 용량을 키우는 방식을 수평 확장이라고 합니다.

숫자로 확인하기

가용성의 숫자 — 1년은 8,760시간이라서 가용성 99.9%는 연 8.76시간, 99.99%는 약 52.6분, 99.999%는 약 5.3분의 정지만 허용합니다.
두 대를 두면 얼마나 좋아지나 — 서버 한 대의 가용성이 99%(정지 확률 0.01)이고 두 대가 서로 독립이라고 가정하면, 둘이 동시에 멈출 확률은 0.01 × 0.01 = 0.0001이라서 서버 쪽 가용성은 99.99%가 됩니다. 로드 밸런서 자체의 가용성과 서버가 공유하는 DB 같은 의존성은 따로 봐야 합니다.
해시와 서버 수 변화 — 키를 서버 수로 나눈 나머지로 서버를 고르면, 서버가 3대에서 4대로 늘 때 키를 균등하게 가정하면 같은 서버에 남는 키는 3/12, 곧 25%뿐이고 75%가 다른 서버로 옮겨 갑니다. 이런 이동을 줄이려고 일관된 해싱(consistent hashing)을 씁니다.
Least Connection 계산 — 서버 A, B, C의 활성 연결이 5, 2, 8개이면 다음 요청은 B로 갑니다. 가중치 3:1:1의 Weighted Round Robin이라면 5개 요청 중 3개가 첫 서버로 갑니다.

자주 하는 오해

로드 밸런서를 두면 장애가 없어진다 — 로드 밸런서가 단일 장애 지점이 될 수 있습니다. 그래서 로드 밸런서 자체도 이중화하거나 관리형 서비스를 씁니다.
Round Robin이면 부하가 항상 고르다 — 요청 개수는 고르게 나누지만 요청마다 처리 비용이 다르면 서버 부하는 달라집니다. 이때는 활성 연결 수를 보는 방식이 낫습니다.
L7이 항상 더 좋다 — L7은 내용을 보고 정교하게 나눌 수 있지만, HTTP를 해석해야 해서 처리 비용이 늘고 HTTPS라면 TLS를 끝내야 합니다. 단순한 TCP 분산에는 L4가 적합합니다.
헬스 체크가 200이면 정상이다 — 체크 엔드포인트가 무엇을 확인하느냐에 달려 있습니다. 프로세스만 확인하면 DB 연결이 끊긴 서버를 정상으로 볼 수 있습니다.

면접에서 이렇게 물어요

면접 질문

L4와 L7 로드 밸런서의 차이는 무엇인가요?

L4는 IP와 포트 수준에서 TCP/UDP 연결을 나누어 빠르고 단순합니다. L7은 HTTP 헤더, URL, 쿠키를 읽어 경로별 라우팅이나 쿠키 기반 고정 같은 정교한 분산이 가능하지만 처리 비용이 더 듭니다.

면접 질문

서버에 세션이 있으면 로드 밸런서에서 어떻게 처리하나요?

같은 사용자를 같은 서버로 보내는 고정 세션(sticky session)을 쓰거나, 세션을 Redis 같은 외부 저장소로 빼서 어느 서버로 가도 같은 세션을 읽게 합니다. 고정 세션은 그 서버가 죽으면 세션이 사라지고 부하가 한쪽으로 쏠릴 수 있습니다.

면접 질문

서버 한 대가 죽으면 어떻게 되나요?

헬스 체크가 연속으로 실패하면 로드 밸런서가 그 서버를 대상에서 빼고, 다시 성공하면 복귀시킵니다. 이미 연결된 요청은 실패할 수 있어서 재시도나 연결 종료 대기(draining) 설정이 필요합니다.

면접 질문

로드 밸런서 자체가 죽으면 어떻게 하나요?

Active-Passive로 대기 장비가 가상 IP를 넘겨받게 하거나, Active-Active로 여러 대가 동시에 처리하게 합니다. 클라우드의 관리형 로드 밸런서는 여러 가용 영역에 걸쳐 이중화되어 있습니다.

실제 시스템에서는

nginx upstream — nginx는 기본이 가중치 라운드 로빈이고 least_conn, ip_hash, hash ... consistent 지시어로 방식을 바꿉니다. ip_hash는 IPv4 주소의 앞 세 옥텟을 키로 씁니다. 오픈소스 nginx의 서버 상태 확인은 요청 실패를 보고 판단하는 수동 방식이고 주기적인 능동 확인은 NGINX Plus 기능입니다.
클라우드 서비스 — AWS의 Application Load Balancer는 HTTP/HTTPS를 다루는 L7 방식이고 Network Load Balancer는 TCP/UDP/TLS를 다루는 L4 방식입니다.
Spring Boot 헬스 체크 — Spring Boot Actuator의 /actuator/health 엔드포인트가 애플리케이션과 DB 같은 의존성의 상태를 모아 보여 주므로 헬스 체크 경로로 쓸 수 있습니다.

함께 보면 좋은 토픽

DNS — DNS 라운드 로빈과 로드 밸런서를 비교합니다.
HTTPS / TLS — 로드 밸런서에서 TLS를 끝낼 때의 흐름을 봅니다.
HTTP — L7 분산이 읽는 헤더와 쿠키를 봅니다.
CDN — 엣지에서 트래픽을 나누는 구조를 비교합니다.
WebSocket — 오래 유지되는 연결을 분산할 때의 고려점을 봅니다.
