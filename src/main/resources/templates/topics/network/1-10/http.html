HTTP

태그

HTTP(HyperText Transfer Protocol)는 웹에서 클라이언트와 서버가 데이터를 주고받는 애플리케이션 계층 프로토콜입니다. 무상태(Stateless) 프로토콜로 각 요청은 독립적이며, 버전별로 성능과 기능이 크게 발전해왔습니다.

핵심 개념

요청 / 응답 구조

HTTP 메시지는 요청(Request)과 응답(Response)으로 구성됩니다. 요청은 메서드(GET·POST·PUT·DELETE), URL, 헤더, 바디로 이루어집니다. 응답은 상태 코드(200·404·500), 헤더, 바디로 구성됩니다. 헤더는 Content-Type·Authorization·Cache-Control 등 메타데이터를 포함합니다.

핵심 개념

HTTP/1.1

1997년 RFC 2068로 처음 발표되었고 지금은 RFC 9112로 정리된 버전입니다. 기본적으로 Keep-Alive를 지원해 하나의 TCP 연결로 여러 요청을 처리합니다. 하지만 요청을 순서대로 처리하는 HOL(Head-of-Line) 블로킹 문제가 있습니다. 파이프라이닝을 지원하지만 실제로는 거의 사용되지 않습니다.

핵심 개념

HTTP/2

2015년 RFC 7540으로 표준화됐습니다(현재는 RFC 9113). 멀티플렉싱으로 하나의 TCP 연결에서 여러 요청을 동시에 처리합니다. 헤더 압축(HPACK)으로 오버헤드를 줄이고, 서버 푸시로 클라이언트 요청 전에 리소스를 미리 전송할 수 있도록 설계되었습니다(클라이언트가 끌 수 있고, 성능 이득이 불분명해 Chrome은 106부터 기본으로 꺼 두었습니다). 바이너리 프레이밍 계층을 사용합니다.

핵심 개념

상태 코드

2xx(성공): 200 OK·201 Created·204 No Content. 3xx(리다이렉트): 301 Moved Permanently·302 Found·304 Not Modified. 4xx(클라이언트 오류): 400 Bad Request·401 Unauthorized·403 Forbidden·404 Not Found. 5xx(서버 오류): 500 Internal Server Error·502 Bad Gateway·503 Service Unavailable.

핵심 개념

무상태 & 쿠키/세션

HTTP는 각 요청이 독립적인 무상태 프로토콜입니다. 상태 유지가 필요하면 쿠키(Cookie)를 사용합니다. 서버는 Set-Cookie 헤더로 쿠키를 설정하고, 클라이언트는 이후 요청에 Cookie 헤더로 전송합니다. 세션은 서버 측에서 상태를 관리하며 세션 ID만 쿠키로 전달합니다.

핵심 개념

HTTP/3 & QUIC

2022년 RFC 9114로 표준화됐습니다. TCP 대신 UDP 기반의 QUIC 프로토콜을 사용합니다. 한 스트림의 손실이 다른 스트림을 막는 TCP 수준의 HOL 블로킹을 없애고, 전송과 TLS 1.3 핸드셰이크를 함께 처리해 연결 설정을 줄이며, 이전에 접속한 서버와는 0-RTT 데이터 전송이 가능합니다(재전송 공격에 주의해야 합니다). TLS 1.3이 내장되어 있습니다.

HOL(Head-of-Line) 블로킹 — HTTP/1.1에서 첫 번째 요청이 느리면 뒤의 요청들이 대기해야 합니다. 브라우저는 이를 우회하기 위해 도메인당 여러 개(흔히 6개)의 TCP 연결을 병렬로 열었습니다. HTTP/2의 멀티플렉싱은 TCP 레벨의 HOL은 해결하지 못하고, HTTP/3(QUIC)에서야 완전히 해결됩니다.
캐시 제어 — Cache-Control 헤더로 캐싱 동작을 제어합니다. max-age=3600은 1시간 캐싱, no-cache는 매번 서버 검증, no-store는 캐시 금지입니다. ETag와 Last-Modified로 조건부 요청(304 Not Modified)을 구현해 불필요한 데이터 전송을 줄입니다.
CORS (Cross-Origin Resource Sharing) — 브라우저는 보안 정책상 다른 출처의 리소스 접근을 제한합니다. 서버가 Access-Control-Allow-Origin 헤더를 응답에 포함하면 허용됩니다. GET·HEAD·POST가 아닌 메서드나 허용 목록에 없는 헤더(사용자 정의 헤더 등)가 있는 요청처럼 단순하지 않은 요청은 사전 OPTIONS 요청(Preflight)을 먼저 보냅니다.
REST vs GraphQL — REST는 URL 자원 중심으로 HTTP 메서드를 활용합니다. GraphQL은 단일 엔드포인트에서 클라이언트가 필요한 데이터 형태를 쿼리로 요청합니다. Over-fetching과 Under-fetching 문제를 해결하지만 캐싱이 복잡합니다.

HTTP는 어떻게 발전했나

HTTP는 웹에서 문서를 요청하고 응답하는 단순한 텍스트 프로토콜로 시작해, 같은 요청과 응답의 의미를 유지한 채 전송 방식만 바꿔 가며 발전해 왔습니다. HTTP/1.1은 1997년 RFC 2068로 처음 발표되었고 지금은 RFC 9110(공통 의미)과 RFC 9112(1.1 메시지 형식)로 정리되어 있습니다. HTTP/2(RFC 9113)와 HTTP/3(RFC 9114)는 같은 의미 위에서 더 효율적인 전송을 제공합니다.

숫자로 확인하기

새 연결에서 첫 응답까지의 왕복 수(DNS 조회와 패킷 손실은 뺀 단순화) — TCP 연결에 1 RTT, TLS 1.2 핸드셰이크에 2 RTT(메시지 흐름에서 센 값), 요청과 응답에 1 RTT로 총 4 RTT입니다. TLS 1.3이면 핸드셰이크가 1 RTT라서 3 RTT, HTTP/3은 전송과 TLS 설정을 한 번에 해서 2 RTT입니다. RTT가 100ms이면 400ms, 300ms, 200ms입니다.
상태 코드 분류 — 첫 숫자로 1xx 정보, 2xx 성공, 3xx 리다이렉션, 4xx 클라이언트 오류, 5xx 서버 오류의 다섯 가지로 나뉩니다.
HTTP/1.1의 병렬성 — 한 연결에서는 응답을 요청 순서대로 받으므로, 브라우저는 호스트당 여러 개의 연결을 병렬로 열어 로딩을 빠르게 하려 했습니다. Chromium 문서는 목적지 호스트당 6개 소켓이라고 설명합니다(RFC는 특정 숫자를 두지 않습니다).

자주 하는 오해

HTTP/2나 HTTP/3이면 항상 더 빠르다 — 요청이 많고 작을 때 이득이 크지만, 요청 수가 적거나 네트워크가 좋으면 차이가 작습니다. 손실이 많은 환경에서는 HTTP/3이 유리한 경우가 많습니다.
HTTP가 무상태라서 로그인 상태를 못 쓴다 — 프로토콜은 요청 사이의 상태를 기억하지 않지만, 쿠키나 토큰으로 요청마다 식별 정보를 실어 상태를 만듭니다.
401과 403은 같은 뜻이다 — 401은 인증이 필요하거나 인증에 실패했다는 뜻이고, 403은 인증되어도 권한이 없다는 뜻입니다.
POST와 PUT은 같다 — PUT은 같은 요청을 여러 번 보내도 결과가 같은 멱등(idempotent) 메서드이고, POST는 멱등으로 정의되어 있지 않습니다. GET, HEAD 같은 메서드는 안전(safe)하고 멱등합니다.

면접에서 이렇게 물어요

면접 질문

GET과 POST의 차이는 무엇인가요?

GET은 자원을 읽는 안전하고 멱등한 메서드이고 보통 캐시할 수 있습니다. POST는 서버에 데이터를 보내 처리를 요청하며 결과가 바뀔 수 있고 멱등하지 않습니다. 데이터를 URL에 싣느냐 본문에 싣느냐는 부차적인 차이입니다.

면접 질문

301과 302의 차이는 무엇인가요?

301은 영구 이동, 302는 임시 이동입니다. 검색 엔진과 캐시가 영구 이동은 주소를 바꿔 기억하고, 임시 이동은 원래 주소를 유지합니다.

면접 질문

HTTP/1.1의 HOL 블로킹은 무엇이고 어떻게 줄였나요?

한 연결에서 앞 응답이 늦으면 뒤 응답이 기다리는 문제입니다. HTTP/2는 멀티플렉싱으로 한 연결에서 여러 스트림을 섞어 보내고, HTTP/3은 TCP 대신 QUIC를 써서 한 스트림의 손실이 다른 스트림을 막지 않게 합니다.

면접 질문

CORS 에러는 왜 발생하나요?

브라우저가 다른 출처로 보낸 요청의 응답을 서버가 허용하지 않았을 때 응답을 스크립트에 노출하지 않는 것입니다. 서버가 Access-Control-Allow-Origin 같은 헤더로 허용해야 합니다. GET·HEAD·POST가 아닌 메서드, 허용 목록에 없는 헤더, form·multipart·text/plain이 아닌 Content-Type 같은 요청은 먼저 OPTIONS 사전 요청(preflight)을 보냅니다.

실제 시스템에서는

캐시 — RFC 9111이 HTTP 캐시의 규칙을 정의하고, Cache-Control, ETag, 조건부 요청(If-None-Match)으로 304 응답을 이끌어냅니다.
CORS — 브라우저가 따르는 CORS 규칙과 사전 요청의 조건은 WHATWG Fetch 표준이 정의합니다.
HTTPS와 CDN — 실제 서비스는 보통 TLS 위에서 HTTP를 쓰고 CDN을 거칩니다. HTTPS / TLS와 CDN 토픽에서 이어서 봅니다.

함께 보면 좋은 토픽

TCP/IP — HTTP가 올라타는 연결 설정과 전송 방식을 봅니다.
HTTPS / TLS — HTTP에 암호화를 더하는 방식을 봅니다.
DNS — 요청 전에 이름을 주소로 바꾸는 과정을 봅니다.
CDN — HTTP 캐시를 이용해 응답을 가까이 두는 방식을 봅니다.
WebSocket — HTTP 연결에서 양방향 통신으로 넘어가는 방식을 봅니다.
