DNS

태그

DNS(Domain Name System)는 사람이 읽을 수 있는 도메인 이름을 IP 주소로 변환하는 인터넷의 전화번호부입니다. 계층적 구조로 이루어진 분산 데이터베이스로, 전 세계 수십억 건의 질의를 처리합니다.

핵심 개념

재귀 질의 흐름

브라우저가 example.com을 입력하면 로컬 DNS 리졸버에 질의합니다. 캐시에 없으면 루트 DNS → .com TLD DNS → example.com 권한 DNS 순서로 재귀 질의합니다. 최종적으로 IP 주소를 받아 브라우저에 반환하고, 결과를 TTL 동안 캐시합니다.

핵심 개념

DNS 계층 구조

DNS는 역트리 구조입니다. 루트(.)가 최상위이고, .com·.org·.kr 같은 TLD(Top Level Domain), 그 아래 example.com 같은 2차 도메인, www·mail 같은 서브도메인 순서입니다. 각 계층의 네임서버가 자신의 영역(Zone)에 대한 정보를 관리합니다.

핵심 개념

DNS 레코드 종류

A: 도메인 → IPv4 주소. AAAA: 도메인 → IPv6 주소. CNAME: 도메인 → 다른 도메인(별칭). MX: 메일 서버 지정. NS: 네임서버 지정. TXT: 임의 텍스트(SPF·DKIM 등). PTR: IP → 도메인(역방향 조회). SOA: 존의 권한 시작 정보.

핵심 개념

TTL과 캐싱

TTL(Time To Live)은 DNS 레코드의 캐시 유효 시간(초)입니다. TTL=300이면 5분간 캐시에 저장됩니다. 짧은 TTL은 빠른 변경 반영을 가능하게 하지만 DNS 서버 부하를 증가시킵니다. 브라우저·OS·로컬 DNS 리졸버 등 여러 단계에서 캐싱이 발생합니다.

핵심 개념

재귀 vs 반복 질의

재귀 질의(Recursive): 클라이언트가 로컬 리졸버에 요청하면, 리졸버가 최종 답을 찾아 반환합니다. 클라이언트는 한 번만 요청합니다. 반복 질의(Iterative): 각 DNS 서버가 다음에 물어볼 서버 주소를 알려주고, 클라이언트가 직접 순서대로 질의합니다. 실제로는 두 방식이 혼합됩니다.

핵심 개념

DNS 보안 (DNSSEC)

기본 DNS는 UDP 53번 포트를 사용하며 암호화가 없어 스푸핑·캐시 포이즈닝에 취약합니다. DNSSEC은 디지털 서명으로 응답의 출처와 무결성을 검증합니다(내용을 암호화하지는 않습니다). DoH(DNS over HTTPS)와 DoT(DNS over TLS)는 DNS 질의 자체를 암호화해 프라이버시를 보호합니다(암호화되는 구간은 클라이언트와 리졸버 사이입니다).

루트 DNS 서버 — 루트 네임서버는 A부터 M까지 13개의 이름으로 운영되며, 각 이름은 전 세계 여러 곳의 서버가 같은 주소를 쓰는 애니캐스트로 제공됩니다(root-servers.org는 2,000개 이상의 인스턴스가 운영 중이라고 안내합니다). 루트 서버는 TLD 서버 주소만 알고 있으며, 직접 IP를 반환하지 않습니다. 루트 존의 내용(TLD 위임)은 IANA가 관리하고, 루트 서버 운영은 여러 독립 기관이 나눠 맡습니다.
DNS 캐시 포이즈닝 — 공격자가 가짜 DNS 응답을 주입해 캐시를 오염시키는 공격입니다. 카민스키 공격(2008)으로 심각성이 알려졌습니다. 랜덤 소스 포트와 트랜잭션 ID, DNSSEC 등으로 방어합니다.
글루 레코드 (Glue Record) — 네임서버 도메인이 자신이 관리하는 존에 속할 때 발생하는 닭과 달걀 문제를 해결합니다. 부모 존에 네임서버의 IP를 직접 포함시켜 순환 참조를 방지합니다.
DNS 라운드 로빈 — 같은 도메인에 여러 A 레코드를 등록하면 DNS 서버가 순서를 바꿔가며 응답해 트래픽을 분산합니다. 단순하지만 기본 방식은 서버 상태를 확인하지 않아 장애 서버 주소도 돌려줄 수 있습니다.

DNS가 필요한 이유

사람은 이름을 기억하고 네트워크는 숫자 주소로 통신합니다. DNS는 도메인 이름을 IP 주소 같은 정보로 바꿔 주는, 전 세계에 분산된 계층형 데이터베이스입니다. 이름과 주소가 분리되어 있어서 서버의 주소를 바꿔도 이름은 그대로 쓸 수 있습니다. 기본 설계는 RFC 1034와 RFC 1035에 정의되어 있습니다.

숫자로 확인하기

이름의 길이 제한 — 도메인 이름의 각 레이블(점으로 나뉜 한 마디)은 최대 63바이트이고, 전체 이름은 255바이트(점 표기에서 대개 253자)까지입니다.
UDP 응답 크기 — 원래 DNS의 UDP 메시지는 512바이트로 제한되었고, EDNS(0) 확장으로 더 큰 크기를 협상합니다. 응답이 너무 크면 TCP로 다시 질의합니다.
TTL의 영향 — TTL이 300초이면 변경한 레코드가 캐시를 가진 리졸버에서 최대 5분 뒤에 바뀝니다. 86,400초(하루)이면 최대 하루입니다. 서버를 옮기기 전에 TTL을 낮춰 두면 전환 시간을 줄일 수 있습니다.
이름 하나를 찾을 때의 질의 — 캐시가 전혀 없을 때 www.example.com을 찾으려면 리졸버는 루트, .com, example.com 권한 서버 순으로 묻습니다(위임이 더 깊거나 CNAME이 있으면 단계가 늘어납니다). 캐시가 있으면 이 단계들이 생략됩니다.

자주 하는 오해

DNS는 UDP만 쓴다 — 기본은 UDP 53이지만 응답이 크거나 영역 전송 같은 경우에는 TCP도 씁니다.
DNS 변경은 전 세계에 '전파'된다 — 서버가 값을 밀어 보내는 것이 아니라, 각 캐시의 TTL이 만료되면 새로 물어서 바뀝니다. 그래서 반영 시간이 캐시마다 다릅니다.
도메인의 루트(apex)에도 CNAME을 쓸 수 있다 — CNAME이 있는 이름에는 다른 레코드를 둘 수 없습니다. 존 꼭대기(apex)에는 SOA와 NS가 있으므로 CNAME을 쓸 수 없습니다.
DNSSEC이면 질의 내용이 암호화된다 — DNSSEC은 응답이 진짜인지 서명으로 검증할 뿐 내용을 숨기지 않습니다. 숨기는 것은 DoH나 DoT의 역할입니다.

면접에서 이렇게 물어요

면접 질문

브라우저에 주소를 입력하면 DNS는 어떻게 동작하나요?

브라우저와 OS 캐시를 먼저 보고, 없으면 설정된 리졸버에 질의합니다. 리졸버는 캐시가 없으면 루트, TLD, 권한 네임서버 순으로 물어 IP를 얻어 돌려주고 TTL 동안 저장합니다.

면접 질문

재귀 질의와 반복 질의의 차이는 무엇인가요?

재귀는 클라이언트가 리졸버에 한 번 묻고 최종 답을 받는 방식이고, 반복은 질의를 받은 서버가 다음에 물을 서버를 알려 주고 질의자가 직접 따라가는 방식입니다. 실제로는 클라이언트와 리졸버 사이는 재귀, 리졸버와 권한 서버 사이는 반복으로 섞여 있습니다.

면접 질문

CNAME과 A 레코드의 차이는 무엇인가요?

A는 이름을 IPv4 주소로 직접 연결하고, CNAME은 이름을 다른 이름의 별칭으로 만듭니다. CNAME 대상의 최종 주소는 다시 조회해야 합니다.

면접 질문

DNS 캐시 포이즈닝은 어떻게 막나요?

응답이 요청과 맞는지 확인하도록 질의마다 무작위 트랜잭션 ID와 소스 포트를 쓰고, DNSSEC 서명을 검증하며, DoT나 DoH로 질의 경로를 보호합니다.

실제 시스템에서는

dig 명령 — dig로 레코드 종류와 TTL을 확인하고 +trace 옵션으로 루트부터의 위임 과정을 따라가 볼 수 있습니다.
JVM의 DNS 캐시 — 자바의 InetAddress는 조회 결과를 캐시하고 기간은 java.security의 networkaddress.cache.ttl 보안 속성으로 조절한다고 문서가 설명합니다. DNS 레코드를 바꿨는데 애플리케이션이 이전 주소를 계속 쓴다면 이 캐시를 의심해 볼 수 있습니다.
루트 서버와 애니캐스트 — 루트 서버는 A부터 M까지 13개의 이름으로 운영되고, 각 이름은 전 세계 여러 곳의 서버가 같은 주소를 쓰는 애니캐스트로 제공됩니다.
