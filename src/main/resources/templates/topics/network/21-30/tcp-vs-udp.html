TCP vs UDP와 흐름 제어

태그

인터넷에서 두 프로그램이 데이터를 주고받으려면 IP 위에서 어떤 방식으로 보낼지 정해야 합니다. 이때 가장 많이 쓰는 전송 계층 프로토콜이 TCP(Transmission Control Protocol)와 UDP(User Datagram Protocol)입니다. TCP는 연결을 만들고, 보낸 데이터가 순서대로 빠짐없이 도착하도록 책임집니다. UDP는 그런 약속 없이 데이터를 한 덩어리씩 던지듯 보냅니다. 웹 페이지와 파일 전송은 대개 TCP로, 이름 조회(DNS)와 실시간 음성 · 영상은 UDP로 가는 이유가 여기에 있습니다.

이 토픽에서는 TCP의 3-way handshake와 순서 번호 · 확인 응답 · 재전송, 연결 종료의 4단계, UDP가 연결 없이 데이터그램을 보내며 유실을 책임지지 않는 모습, 그리고 수신 측이 윈도 크기로 송신 속도를 조절하는 흐름 제어를 단계별로 봅니다.

핵심 개념

연결형과 비연결형

TCP는 데이터를 보내기 전에 양쪽이 연결 상태를 만들고 유지합니다. UDP는 연결 상태가 없어서 보내고 싶을 때 바로 데이터그램을 보냅니다.

핵심 개념

바이트 스트림과 데이터그램

TCP는 바이트가 이어진 흐름을 전달하므로 보낸 단위와 받는 단위가 같다고 보장하지 않습니다. UDP는 보낸 데이터그램 하나가 받는 쪽에 한 덩어리로 전달됩니다.

핵심 개념

순서 번호와 확인 응답

TCP는 보낸 바이트마다 번호를 매기고, 수신 측이 "다음에 받을 번호"를 ack로 알립니다. 확인이 오지 않으면 송신 측이 같은 데이터를 다시 보냅니다.

핵심 개념

3-way handshake

SYN, SYN-ACK, ACK 세 번의 교환으로 양쪽이 서로의 초기 순서 번호를 확인하고 연결을 만듭니다. 연결을 닫을 때는 FIN과 ACK를 양방향으로 주고받습니다.

핵심 개념

흐름 제어

수신 측이 ACK에 수신 윈도(받을 수 있는 크기)를 실어 알리고, 송신 측이 확인받지 못한 데이터를 그 크기 이하로만 유지해 수신 버퍼가 넘치지 않게 합니다.

핵심 개념

혼잡 제어

네트워크가 붐비지 않도록 송신 측이 혼잡 윈도로 보내는 양을 스스로 조절하는 장치입니다. 흐름 제어가 수신 측을 지킨다면 혼잡 제어는 네트워크를 지킵니다.

TCP의 신뢰성은 번호와 확인 응답에서 나옵니다 — 번호가 있어서 수신 측이 순서를 맞추고 중복을 버리고, 확인이 없으면 재전송할 수 있습니다.
UDP는 가벼운 대신 책임지지 않습니다 — 헤더가 작고 기다리는 단계가 없지만, 유실 · 중복 · 순서 뒤바뀜을 UDP는 처리하지 않으므로 필요하면 애플리케이션이 직접 다룹니다.
TCP는 메시지 경계를 만들어 주지 않습니다 — 애플리케이션 프로토콜이 길이나 구분자로 한 메시지의 끝을 직접 정해야 합니다.
신뢰성이 필요한지가 선택 기준입니다 — 한 바이트도 틀리면 안 되는 데이터는 TCP, 조금 잃어도 최신 데이터가 중요하거나 요청과 응답이 한 번씩이면 끝나는 경우는 UDP가 맞을 수 있습니다.
이 시각화에서 확인할 것 — "TCP 연결·전송" 탭에서 handshake, 유실과 재전송, 연결 종료를, "UDP 전송" 탭에서 유실을 아무도 모르는 모습을, "흐름 제어" 탭에서 윈도가 0이 됐다가 다시 열리는 과정을 STEP으로 확인하세요.

배경

UDP는 1980년 RFC 768로 정의됐습니다. 문서 3쪽 분량의 단순한 프로토콜로, IP 위에서 포트 번호로 프로그램을 구분해 데이터그램을 전달하는 것이 전부입니다. TCP는 1981년 RFC 793으로 표준화됐고, 오랫동안 고쳐진 끝에 2022년 RFC 9293이 이를 대체하는 현재의 명세가 됐습니다. 신뢰할 수 없는 IP 네트워크 위에서 신뢰할 수 있는 바이트 스트림을 만들어 내는 것이 TCP의 목표였습니다. 혼잡 제어 알고리즘은 RFC 5681에, 큰 윈도를 쓰는 확장은 RFC 7323에 정리돼 있습니다.

숫자로 확인하기

헤더 크기 — UDP 헤더는 출발 포트, 도착 포트, 길이, 체크섬 각 2바이트씩 8바이트입니다. TCP 헤더는 옵션이 없어도 20바이트이고, 옵션이 붙으면 최대 60바이트까지 늘어납니다.
포트 번호 — 두 프로토콜 모두 포트가 16비트라 0부터 65535까지입니다. 같은 번호라도 TCP 포트와 UDP 포트는 서로 다른 것으로 취급됩니다.
연결 수립과 종료의 세그먼트 수 — 연결을 만드는 데 세 개(SYN, SYN-ACK, ACK), 양쪽을 모두 닫는 데 보통 네 개(FIN, ACK, FIN, ACK)가 오갑니다. 가운데 ACK와 FIN을 한 세그먼트에 합치면 세 개가 되기도 합니다.
수신 윈도의 한계 — TCP 헤더의 윈도 필드는 16비트라 한 번에 알릴 수 있는 크기가 65,535바이트입니다. 윈도 확장 옵션(RFC 7323)은 이 값을 최대 2의 14제곱 배까지 키워 약 1GiB까지 알릴 수 있게 합니다.
UDP 데이터그램의 최대 크기 — 길이 필드가 16비트라 헤더를 포함해 65,535바이트가 한계입니다. IPv4에서는 IP 헤더 20바이트와 UDP 헤더 8바이트를 빼면 데이터는 최대 65,507바이트입니다.

자주 하는 오해

UDP는 패킷을 잘 잃어버리는 프로토콜이다 — UDP가 유실을 일으키는 것이 아니라, 네트워크에서 생긴 유실을 복구해 주지 않을 뿐입니다. 네트워크 상태가 좋으면 UDP로도 대부분 잘 도착합니다.
TCP는 데이터가 반드시 전달됨을 보장한다 — 연결이 끊기거나 재전송이 계속 실패하면 TCP는 전달을 포기하고 오류를 알립니다. 보장하는 것은 "전달된다면 순서대로 빠짐없이"이고, ACK는 상대의 TCP가 받았다는 뜻이지 애플리케이션이 처리했다는 뜻이 아닙니다.
write를 두 번 하면 read도 두 번 된다 — TCP는 바이트 스트림이라 두 번 보낸 데이터가 한 번에 읽히거나, 한 번 보낸 데이터가 나뉘어 읽힐 수 있습니다. 메시지 경계는 애플리케이션이 정해야 합니다.
흐름 제어와 혼잡 제어는 같은 말이다 — 흐름 제어는 수신 측 버퍼가 넘치지 않게 수신 측이 알려 주는 윈도로 조절하고, 혼잡 제어는 네트워크 경로가 막히지 않게 송신 측이 스스로 추정해 조절합니다.

실제 시스템에서는

웹과 서비스 통신 — HTTP/1.1과 HTTP/2, SSH는 TCP 위에서 동작하고, 데이터베이스 클라이언트 연결도 대개 TCP를 씁니다. HTTP/3는 UDP 위에 만든 QUIC을 전송 계층으로 쓰고, QUIC이 재전송과 혼잡 제어를 자체로 수행합니다.
UDP를 쓰는 서비스 — DNS 조회, DHCP, NTP 시각 동기화, RTP 기반 실시간 음성 · 화상 통화가 대표적입니다. 실시간 통화에서는 늦게 도착한 오래된 데이터를 다시 받는 것보다 지금의 데이터를 이어 가는 것이 중요합니다.
Java 소켓 — TCP는 Socket과 ServerSocket, UDP는 DatagramSocket과 DatagramPacket으로 다룹니다. TCP 소켓의 InputStream에서 읽는 단위는 보낸 write 단위와 무관합니다.
연결 상태 확인 — 리눅스에서 ss -tan으로 ESTAB(ESTABLISHED), TIME-WAIT 같은 TCP 상태를 볼 수 있고, Wireshark나 tcpdump로 SYN, ACK, FIN 세그먼트와 순서 번호를 직접 확인할 수 있습니다.

TCP 혼잡 제어 — 이 토픽에서 구분만 한 혼잡 윈도의 증가와 감소를 자세히 봅니다.
